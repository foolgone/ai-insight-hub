> 版本口径：`version=v1.2.4`、`rubric_version=v1.2.0`、Schema v3、Metric v3、target v1.0.2、default v1.0.0。
> v1.2.3 保持 `frozen`，不修改、不重跑；M1-D-5 diagnostic `blocked`、未 verified。

## 1. 结论

v1.2.3 的 Agent 预校验已经证明了“Agent 能看到 quote 错误”：

- Q23 首次输出 cl2/cl3 被记录 2 条 `quote_not_found`；
- Agent 触发 1 次 repair；
- repair 输出在 Schema 阶段失败（`contradiction_with` / `evidence_refs` 写成字符串）。

只读诊断进一步证明：**即使把字符串还原成数组，repair 也不是纯格式修复**：

- repair 已把 cl2/cl3 的 quote 改成合法连续子串；
- 但把 cl1 从 `supported` 改成 `insufficient_evidence`；
- F coverage 从 0.5 掉到 0.333，Q23 仍 target miss。

因此 v1.2.4 不能做“字符串转数组”的 normalization，也不能继续让 repair 返回完整 claims JSON。必须改成：

**Evidence-only patch repair：patch 只含 claim_id + context_id + quote；合并时只替换被标记 claim 的 `evidence_refs`；其它字段逐字保留。**

同时补两条：

1. `StructuredOutputError.validation_errors` 接入 `agent_contract.final_errors`；
2. C prompt 增加“首句/结论 wrong_facts → 固定 0.0–0.2”的通用优先级。

## 2. 根因

| 层 | 事实 |
|---|---|
| Agent 预校验 | 生效；首次输出抓到 cl2/cl3 quote 错误 |
| repair | 返回完整 claims JSON，模型顺手改了 cl1 `support_status` |
| Schema | repair 输出数组字段写成字符串，Pydantic 失败 |
| final_errors | Schema 失败发生在 `_validate_parsed` 之前，contract_report 没有真实最终错误 |
| C | Q23 C=0.3，模型把“首句矛盾”判成 0.3–0.4，而不是 0.0–0.2 |
| 账本 | 本次 shell 中断导致 4 calls 可能只是下限，不能作为 10 条预算依据 |

## 3. 目标与非目标

### 3.1 目标

1. quote 错误只触发 evidence-only patch，不生成完整 claims。
2. patch 不能改变 claim 文本、类型、子类型、support_status、矛盾字段。
3. patch 失败（未知 claim、非连续 quote、额外字段、字段类型错误）→ invalid，不降级。
4. invalid F / F_strict 的 `agent_contract.final_errors` 含真实 Schema/validation 错误。
5. C prompt 首句/结论冲突固定 0.0–0.2；目标不变。
6. 调用账本可审计，中断调用标记 `uncertain_call=true`。
7. 版本隔离：仅 v1.2.4；v1.2.0/1/2/3 行为逐字不变。

### 3.2 非目标

- 不修改 v1.2.3 frozen 资产；
- 不在 v1.2.3 上重跑；
- 不做字符串转数组 normalization；
- 不改 Service invalid 契约、Schema v3、Metric v3、r2、target、fixture；
- 不激活 v1.2.4、不跑 10/40；
- 不让 patch 自动改写 quote 或做模糊匹配。

## 4. P0：Evidence-only patch repair

### 4.1 Patch Schema

新增一个独立 Pydantic Schema（建议 `app/schemas/agents/rag_judge_patch.py`）：

```python
class EvidenceFix(BaseModel):
    model_config = ConfigDict(extra="forbid")
    claim_id: str
    context_id: str
    quote: str


class EvidencePatch(BaseModel):
    model_config = ConfigDict(extra="forbid")
    fixes: list[EvidenceFix] = Field(min_length=1, max_length=20)
```

硬约束：

- 只有 `fixes`；没有 claim 文本、type、subtype、support_status、is_contradictory、contradiction_with；
- `extra="forbid"`：模型若输出 `support_status`、`claim` 等字段，直接 Schema 失败；
- 每个 `claim_id` 最多一条 fix；重复 claim_id → invalid；
- `claim_id` 必须属于本次预校验报错的 claim 集合；未知 claim → invalid；
- `context_id` + `quote` 用共享 quote validator 再验；非连续 → invalid；
- patch 不创建、不删除、不重排 claims。

`patch_schema_sha256` 在 freeze record 记录；建议对 Schema 文件取 SHA256。

### 4.2 触发与流程

仅 `prompt_version == "v1.2.4"` + `faithfulness` + 预校验发现 quote 错误时：

```text
首次完整输出（Schema 解析，不做 full-output repair）
  ↓
Agent quote 预校验（shared validator）
  ├─ 无 quote 错误 → 正常返回
  └─ 有 quote 错误
        ↓
  生成 patch 请求（只含被标记 claim + context excerpts + patch 示例）
        ↓
  1 次 patch 模型调用（不嵌套 full repair）
        ↓
  Patch Schema 解析
        ↓
  claim_id 白名单 + shared quote validator 再验
        ↓
  合并：只替换目标 claim 的 evidence_refs
        ↓
  重新构造完整输出并做最终 Schema/合同校验
        ↓
  通过 → 返回；失败 → StructuredOutputError → invalid
```

关键实现点：

- 首次完整输出用 `max_attempts=1` 解析，避免 Schema 错误时又走 full-output repair；
- quote 错误时 **不调用** `parse_with_repair` 的完整输出修复；
- patch 调用只允许 1 次；patch 自身 Schema 失败不再 repair；
- 合并后重新走完整 Schema + 预校验；Service 仍是最终权威。

### 4.3 合并不变量

合并函数只允许：

```python
merged_claims = deepcopy(original_claims)
for fix in patch.fixes:
    claim = by_id[fix.claim_id]
    claim["evidence_refs"] = [{"context_id": fix.context_id, "quote": fix.quote}]
```

禁止：

- 修改 `claim`、`claim_type`、`claim_subtype`、`support_status`、`is_contradictory`、`contradiction_with`；
- 修改未标记 claim；
- 新增/删除 claim；
- 改变 claim 顺序；
- 改 `reason`。

测试必须对合并前后除目标 `evidence_refs` 外的所有字段做逐字段相等断言。

### 4.4 失败语义

| 失败 | 结果 |
|---|---|
| patch 未知 claim_id | `StructuredOutputError` → invalid |
| patch 重复 claim_id | invalid |
| patch quote 非连续 | invalid |
| patch 含 `support_status` 等额外字段 | Schema 失败 → invalid |
| patch 字段写成字符串 | Schema 失败 → invalid |
| patch 调用仍失败 | invalid，不降级、不 drop |
| patch 成功但 Service 复核失败 | Service invalid |

不允许“patch 失败后退回原输出继续计分”；原 quote 错误仍在。

### 4.5 与 mixed sentence 的边界

- v1.2.4 patch repair **只处理 quote 错误**。
- `insufficient_evidence` 混合句继续 warning + 记录，不触发 patch。
- `supported` 混合句不能由 evidence patch 修复；v1.2.4 不启动 full-output repair，记录为 `mixed_sentence_requires_review` 并按现有 invalid/停止规则处理。
- 这是有意的边界：不用 patch 做 claim 拆分，避免再次语义漂移。

## 5. P0：final_errors 补齐

当前 `StructuredOutputError` 有 `validation_errors`，但 `_validate_parsed` 没执行，导致 `agent_contract.final_errors=[]`。

设计：

1. `AgentResult` 增加 `validation_errors: str | None`（或写入 metadata），由 BaseAgent 的异常分支从 `getattr(exc, "validation_errors", None)` 复制。
2. `RagJudgeAgent` 在 patch/Schema 失败时写：
   ```python
   contract_report["final_errors"] = [{
       "code": "patch_schema_invalid",
       "error_type": type(exc).__name__,
       "validation_errors": getattr(exc, "validation_errors", None),
   }]
   ```
3. Service 失败分支保持 `details.agent_contract`；`_strict_details` 继续携带该字段。
4. 验收断言：patch 字段写成字符串时，invalid F **和 F_strict** 的 `agent_contract.final_errors` 非空，且含真实错误文本。

## 6. P1：C prompt 首句冲突硬上限

### 6.1 规则

在 v1.2.4 `answer_correctness.txt` 增加通用优先级（不引用 Q23）：

- 若 `wrong_facts` 非空，且其中任一项是回答首句/最终结论；
- 即使后文有正确细节，`score` 固定 `0.0–0.2`；
- 不得按“无依据的确定性结论”判 `0.3–0.4`；
- `missing_points` 记录因首句矛盾而缺失的正确结论。

合成示例（不使用任何 gate case 文本）：

- 金标：“不能按 30 天激活条款处理。延保卡需在购买后 30 天内激活。”
- 回答：“可以按延保政策处理。但第 40 天已超过 30 天。”
- 判定：`score=0.0–0.2`，`wrong_facts=["可以按延保政策处理"]`。

### 6.2 一致性 warning（不采用 C repair）

v1.2.4 选择 **warning + 记录**，不新增 C repair：

- 若 `wrong_facts` 命中 answer 首句且 `score > 0.2`，在 `details` 记录 `correctness_first_sentence_warning`；
- 不覆盖模型分数，不静默；
- 若实际仍出现 0.3，报告可见，下一版再单独设计 C repair。

风险：提示词规则不保证模型一定服从；但避免 C full-output repair 再次语义漂移。

### 6.3 C 资产与泄漏

- C prompt 修改，SHA 变化；rubric_version 仍 v1.2.0；
- 必须重跑 10 case 泄漏审计，findings=0；
- C target 不改，仍 `[0.0, 0.2]`。

## 7. P2：调用账本

v1.2.4 的诊断 driver 必须写 append-only ledger（JSONL）：

```json
{"attempt_id":"...","case_id":"Q23","metric":"faithfulness","kind":"primary","started_at":"...","prompt_version":"v1.2.4","model":"qwen-max","uncertain_call":false}
```

规则：

- 每次模型调用前写 `started`；返回后写 `finished` / token / cost；
- 进程中断留下 started 无 finished → `uncertain_call=true`；
- 预算审计按 started 计数，不按 finished 计数；
- 10 条申请必须引用 ledger SHA 与 total attempts；
- 不再使用“4 calls 可能是下限”的不可审计数字。

## 10. 测试与验收

### 10.1 Patch 正向

- 本次 Q23 首次输出 → patch 只改 cl2/cl3 → cl1 仍 `supported` → F=0.5；
- 合并前后除 cl2/cl3 `evidence_refs` 外逐字段相等；
- Service 复核通过，Q23 F evaluated。

### 10.2 Patch 反向

- patch 试图改 cl1 support_status → Schema 额外字段拒绝 → invalid；
- patch quote 非连续 → invalid；
- patch 字段写成字符串 → Schema 失败 → invalid；
- invalid F/F_strict 的 `agent_contract.final_errors` 含真实错误；
- patch 未知/重复 claim_id → invalid；
- 1 次 patch 后失败不重试。

### 10.3 版本隔离

- v1.2.0/1/2/3 不触发 patch；旧 repair SHA 不变；
- v1.2.3 frozen 资产未改；
- v2 路径未改。

### 10.4 C prompt

- 首句 contradiction synthetic → 0.0–0.2；
- `wrong_facts` 首句但 score>0.2 → warning 记录；
- C target 不变；
- 泄漏审计 0 findings；
- C SHA 与 MANIFEST/validation 一致。

### 10.5 账本

- 每次调用写 started/finished；
- 模拟中断 → `uncertain_call=true`；
- 预算按 started 计数；
- ledger SHA 进入报告。

> 状态：`design_scope_pending_review`；**未实现、未改 Prompt/Agent、未 freeze、未跑 Judge。**
> 日期：2026-11-23
> 决策来源：`docs/repair/50-m1d6-q23-root-cause-and-target-review.md`；已选 B + C。
> 版本口径：`version=v1.2.5`、`rubric_version=v1.2.0`、Schema v3、Metric v3、target v1.0.2、default v1.0.0。
> v1.2.4 及更早：保持 `frozen`，资产逐字不变；v1.2.4 `active=false`、默认仍 `v1.0.0`。

## 1. 结论

Q23 的 `0.333` 不是 patch 能修的：patch 只改 `evidence_refs`，不改 `support_status`，也不合并 claim。

本设计的核心是：

1. **F Prompt 增加 claim 分解规则**：一个派生结论 = 一条 `derived` claim；前提与结论不得拆成“前提 insufficient + 结论 supported”。
2. **F Prompt 增加内部矛盾标注规则**：首句/结论与后文关键事实冲突时，`is_contradictory=true`，`contradiction_with` 指向冲突 claim。
3. **patch 健壮性作为配套**：允许 unsupported/insufficient 返回空 refs；supported 仍强制非空；找不到直接 quote 时返回显式 refusal，而不是 `null`；refusal 映射为 invalid。
4. **C / R Prompt 不变**：从 v1.2.4 逐字复制，SHA 不变。
5. **target 不变**：仍 v1.0.2；本设计不产生 v1.0.3。

预期 Q23 S1 形态：`cl1 unsupported`、`cl2 supported`、`cl3/cl4` 合并为 1 条 `derived supported`、`cl5 insufficient`、`cl7 insufficient`；scorable=5、supported=2 → **F=0.400**，落在 `[0.4, 0.5]`。

- 不修改 Schema v3 / Metric v3 / Service invalid 契约；
- 不修改 v1.2.0–v1.2.4 frozen 资产；

## 3. P0-A：F Prompt claim 分解规则

### 3.1 新规则（拟加入 `faithfulness.txt` 第 7 节）

```text
### 7.1 派生结论原子性（硬规则）

- 一个派生结论 = 一条 derived claim。前提与结论必须在同一条 claim 内。
- 不得把同一个派生结论拆成两条，尤其不得出现“前提 insufficient + 结论 supported”的重复计数。
- 如果前提来自 query（如天数、金额、商品类型），且结论由文档规则推导：
  - 只建一条 derived claim；
  - evidence_refs 引用推导所依据的规则原文；
  - 前提本身不单独建 claim，除非它包含独立于结论的事实。
- 只有两个判断可以各自独立成立、且分别有独立规则/证据时，才拆成两条。
- 同一句中的多个独立事实仍按第 7 节拆分；本规则只约束“同一派生结论的前提+结论”。
```

### 3.2 合成示例（不得使用 Q23 文本）

```text
query：购买后第 40 天还能激活延保卡吗？
context C1：延保卡需在购买后 30 天内激活。
answer：不能。购买后第 40 天已超出 30 天激活期限。

正确：
- cl1：购买后第 40 天已超出 30 天激活期限
  claim_type=factual_claim, claim_subtype=derived, support_status=supported
  evidence_refs=[{context_id:"C1", quote:"延保卡需在购买后 30 天内激活。"}]

错误：
- cl1：购买后第 40 天（insufficient）
- cl2：已超出 30 天激活期限（supported）
  同一派生结论被拆成两条，重复进入 F 分母。
```

### 3.3 设计约束

- 不把“合并 claim”做成 Agent 代码逻辑；claim 分解由 Prompt 驱动，patch 仍只改 evidence。
- 不改变 `derived` 的语义定义；只明确“一个派生结论一条 claim”。
- 不改 `claim_subtype` 枚举、Schema v3、Service 计数公式。
- 新规则必须用合成示例；泄漏审计 0 findings。

## 4. P0-B：内部矛盾标注规则

### 4.1 新规则（拟加入 `faithfulness.txt` 第 6 节）

```text
### 6.1 首句/结论与后文冲突（硬规则）

- 回答首句/最终结论与后文关键事实冲突时：
  - 该 claim 的 is_contradictory=true；
  - contradiction_with 填写冲突 claim 的 claim_id；
  - support_status 仍按证据判断，通常为 unsupported。
- “可以/支持/满足” vs “不可以/不支持/不符合”是典型模式；
  不得只判 insufficient 或 unsupported 而不标 is_contradictory。
- 如果冲突 claim 尚未输出，先输出冲突 claim，再填 claim_id。
- 不得把内部矛盾误判为文档冲突（conflict）；文档冲突只在回答披露文档两处规则不一致时使用。
```

### 4.2 合成示例

```text
query：购买后第 40 天还能激活延保卡吗？
context C1：延保卡需在购买后 30 天内激活。
answer：可以激活。……购买后第 40 天已超出 30 天激活期限，因此不能激活。

正确：
- cl1：可以激活
  claim_type=factual_claim, claim_subtype=policy, support_status=unsupported
  is_contradictory=true, contradiction_with=["cl2"]
- cl2：购买后第 40 天已超出 30 天激活期限
  claim_type=factual_claim, claim_subtype=derived, support_status=supported
  evidence_refs=[{context_id:"C1", quote:"延保卡需在购买后 30 天内激活。"}]
```

### 4.3 设计约束

- 不新增 `contradiction` 字段；沿用 `is_contradictory` / `contradiction_with`。
- `is_contradictory=true` 时 `contradiction_with` 必须非空；`false` 时必须为空（结构校验）。
- 不改变 Service 的 `conflict` 契约；内部矛盾仍按 factual claim 计分。
- 不加入 Q23 的“生鲜/24 小时/拍照反馈”等文本。

## 5. P0-C：Patch 健壮性（配套，不是通过路径）

### 5.1 目标

- unsupported / insufficient_evidence 允许 `evidence_refs: []`；
- supported 仍要求非空；
- 找不到直接 quote 时返回显式 refusal，而不是 `null`；
- refusal 映射为 invalid，不降级、不伪造；
- 仅 v1.2.5 生效；v1.2.4 patch 行为逐字不变。

### 5.2 新 Patch Schema（建议独立文件）

新增 `app/schemas/agents/rag_judge_patch_v125.py`，**不修改** v1.2.4 的 `rag_judge_patch.py`：

```python
class EvidenceFixV125(BaseModel):
    model_config = ConfigDict(extra="forbid")
    claim_id: str = Field(min_length=1, max_length=64)
    evidence_refs: list[EvidenceRef] = Field(default_factory=list, max_length=20)


class EvidenceRefusalV125(BaseModel):
    model_config = ConfigDict(extra="forbid")
    claim_ids: list[str] = Field(min_length=1, max_length=20)
    reason_code: Literal[
        "no_direct_quote",
        "quote_not_contiguous",
        "claim_requires_split",
        "other",
    ]
    reason: str = Field(min_length=1, max_length=500)


class EvidencePatchV125(BaseModel):
    model_config = ConfigDict(extra="forbid")
    fixes: list[EvidenceFixV125] = Field(default_factory=list, max_length=20)
    refusal: EvidenceRefusalV125 | None = None
```

Schema 层规则：

- `fixes` 与 `refusal` 互斥；必须至少有一个；
- `fixes` 内 `claim_id` 唯一；
- `refusal.claim_ids` 必须在本次 quote 错误 claim 集合内；
- 空 `evidence_refs` 是合法的 Schema 值，但是否允许由 Agent 按目标 claim 的 `support_status` 判定。

### 5.3 Agent 合并校验（v1.2.5）

| 目标 claim 状态 | patch evidence_refs | 结果 |
|---|---|---|
| supported | 非空、全部连续 | 允许；替换 refs |
| supported | `[]` | invalid：`patch_empty_refs_for_supported` |
| unsupported | `[]` | 允许；替换为 `[]` |
| unsupported | 非空、全部连续 | 允许；替换 refs |
| insufficient_evidence | `[]` | 允许；替换为 `[]` |
| insufficient_evidence | 非空 | invalid：`patch_refs_for_insufficient`（v3 契约） |
| 任意 | 非连续 / 空 quote / 未知 context | invalid：`patch_quote_invalid` |
| conflict + supported | <2 条或互相嵌套 | invalid：`patch_conflict_refs_invalid` |

refusal 规则：

- 只要 patch 返回 `refusal` → `patch_refused` → invalid；
- refusal 的 `claim_ids` 不合法 → `patch_refusal_invalid`；
- refusal 不得与 fixes 同时出现；
- 不把 refusal 降级为 insufficient；不自动补 quote。

### 5.4 Patch Prompt / Example

新增 v1.2.5 patch system prompt（仅在 `_apply_evidence_patch_v125` 使用）：

```text
你是 RAG Judge 的 evidence patch 修复器（v1.2.5）。
只输出 JSON 对象，结构必须严格为以下二选一：
1) {"fixes":[{"claim_id":"cl2","evidence_refs":[{"context_id":"C1","quote":"..."}]}]}
2) {"refusal":{"claim_ids":["cl2"],"reason_code":"no_direct_quote","reason":"..."}}

规则：
- unsupported / insufficient_evidence 可以返回 evidence_refs: []；
- supported 必须至少 1 条连续 quote；
- 找不到直接支持 supported claim 的连续 quote 时，返回 refusal；
- 不得返回 null，不得伪造 quote，不得用邻近无关 quote。
示例：{"fixes":[{"claim_id":"cl2","evidence_refs":[{"context_id":"C1","quote":"延保卡需在购买后 30 天内激活。"}]}]}
```

- 新 patch example 使用合成延保句；不得出现 Q23/Q21/Q11 文本；
- 新 `patch_schema_sha256`、`patch_example_sha256` 在 freeze record 记录；
- v1.2.4 的 patch schema/example/提示词逐字不变。

## 1. 结论

Q23 的根因不是“又缺一条 Prompt 规则”，而是：

**模型把 answer 的加粗句当作 evidence quote，Agent 在返回前看不到 Service 的 `quote_not_found`，所以 repair 轮已经结束，错误无法反馈给模型。**

v1.2.3 必须同时做两件事：

1. **P0 合同闭环**：Agent 在返回前用 contexts 预校验 evidence quote；失败时通过现有 `parse_with_repair` 做一次定向 repair；Service 仍是最终权威。
2. **P0 Prompt 证据来源规则**：明确 quote 只能从 contexts 连续复制，不能从 answer 的加粗句/引号句/转述中复制。

只做 Prompt 规则、不做 Agent 预校验，仍然没有反馈闭环，第四次纯 Prompt patch 很可能重复 Q23。

## 2. Q23 复核与根因

### 2.1 事实

| 项 | 结论 |
|---|---|
| F | `invalid(contract_violation)`，正确 |
| 错误码 | `quote_not_found` × 3（cl1/cl2/cl3） |
| 停止 | 正确；Q21/Q11 未运行 |
| C / R | evaluated，0.2 / 0.9，目标内 |
| F 目标 | invalid 无分数，`[0.4, 0.5]` 不适用 |
| absence | cl9 正确：`non_factual` + `absence` + `null` + `[]` |
| 混合句 | cl5 仍为 `factual_claim` 内含 absence 表述，未拆 |

### 2.2 关键事实

answer 加粗句：

```text
生鲜食品质量问题需在签收后 24 小时内拍照反馈
```

C1 原句：

```text
生鲜食品签收后不支持无理由退货，质量问题需在签收后 24 小时内拍照反馈。
```

模型 quote 与 answer 加粗句逐字一致，但不是 C1 的连续子串——它删掉了
`签收后不支持无理由退货，`。因此不是“两段远距离拼接”，而是**照抄 answer 的截断句**。Service 判 `quote_not_found` 完全正确，不能放宽。

cl5 `该时限是硬性要求，文档未提及例外情形或宽限期` 也直接照抄 answer 的句子结构，说明同一根因：模型把 answer 的句子当成 evidence。

### 2.3 为什么 v1.2.1 / v1.2.2 没打中

| 版本 | 假设 | 实际 |
|---|---|---|
| v1.2.1 evidence-continuity | 模型在拼接两段 context | Q23 是照抄 answer 截断句 |
| v1.2.2 evidence-directness | quote 语义不够直接 | Q23 的 quote 语义相关，但来源错误 |
| 共同缺口 | Service 计分时才发现 quote 错误 | Agent 的 repair 已结束，模型看不到错误 |

当前链路：

```text
Agent 返回合法 JSON
→ Service 计分时发现 quote_not_found
→ Agent repair 已结束
```

`parse_with_repair` 只处理 Schema/validator 错误；quote 校验在 Service 里，Agent 从未看到 `quote_not_found`。因此再加一条 Prompt 仍然没有反馈闭环。

## 3. v1.2.3 目标与非目标

### 3.1 目标

1. 让 Agent 在返回前看到 quote 错误，并触发一次定向 repair。
2. 用 contexts 原文做严格连续子串校验；不做模糊匹配、不自动改写 quote。
3. Prompt 明确 evidence 只能来自 contexts，不能来自 answer 的加粗句/引号句/转述。
4. 混合句按“supported 硬修复、insufficient 软警告”分层，避免把非契约问题升级成新的 invalid。
5. 版本隔离：v1.2.0/v1.2.1/v1.2.2 行为逐字不变。
6. Service 仍是最终判定；Agent 预校验只触发 repair，不放宽 Service 契约。
7. 为 v1.2.3 单案例、10 条、40 条预留可追溯字段和预算。

### 3.2 非目标

- 不保证 Q23 一次通过；只保证错误能被 Agent 看到并尝试修复，修不好仍 invalid。
- 不修改 Service invalid 契约、Schema v3、Metric v3、r2、target、fixture。
- 不换 Judge 模型；继续 qwen-max、temperature 0.0、max_tokens 8192。
- 不激活 v1.2.3、不改默认版本。
- 不跑 10/40；本轮不跑任何 Judge。

## 4. P0-1：Agent 侧 quote 预校验 + 定向 repair

### 4.1 触发条件与版本隔离

| 项 | 设计 |
|---|---|
| 触发版本 | 仅 `prompt_version == "v1.2.3"` |
| 触发指标 | 仅 `faithfulness` |
| 触发时机 | Agent 返回前，`_validate_parsed` 内 |
| v1.2.0/1/2 | 不进入预校验分支，行为逐字不变 |
| Service | 不变；仍用同一共享校验做最终判定 |

现有 `RagJudgeAgent._create_agent` 已把输入保存到 `self._active_input`（`RagJudgeInput`，含 `contexts`），因此不需要把 contexts 从 Service 注入 Agent，也不新增 Service→Agent 依赖。预校验直接在 `_validate_parsed` 中读取 `self._active_input.contexts`。

### 4.2 共享校验函数

新增纯函数模块：

```text
backend/app/schemas/agents/rag_judge_evidence.py
```

建议接口：

```python
@dataclass(frozen=True)
class QuoteCheck:
    claim_id: str
    context_id: str
    quote: str
    ok: bool
    error: str | None          # quote_not_found / unknown_context_id / empty_quote
    context_excerpt: str | None


def build_context_map(contexts: list[str]) -> dict[str, str]:
    """C1..Cn -> context 原文。"""


def check_quote(
    *,
    quote: str,
    context_id: str,
    context_map: dict[str, str],
    claim_id: str = "",
    excerpt_radius: int = 80,
) -> QuoteCheck:
    """严格连续子串校验；失败时返回对应 context 的窗口。"""


def check_claims_evidence(
    claims: list[Any],
    context_map: dict[str, str],
) -> list[QuoteCheck]:
    """遍历 factual claims 的 evidence_refs。"""


def detect_mixed_absence(claim_text: str) -> bool:
    """检测 factual claim 文本中同时含事实断言与 absence 表述。"""
```

要求：

- 校验语义与 Service 当前一致：`quote.strip() in context.strip()`；不改内部空白，不做模糊匹配。
- `context_excerpt` 用最长公共片段或 quote 首段定位，返回 ±80 字符窗口；只用于 repair 提示，不参与计分。
- 服务层 `_v3_claim` 改为调用同一 `check_quote`；错误码、错误消息、降级行为保持与当前完全一致。
- 共享模块不 import `app.services` / `app.agents`；放在 `schemas` 层，`agents` 与 `services` 都可依赖，满足 import-linter。
- 必须有 parity tests：同一组 quote（连续、非连续、错 context、空 quote、answer 截断句）在共享函数与 Service 中得到相同的 `ok/error`。

### 4.3 `_validate_parsed` 行为

v1.2.3 + faithfulness 时，在现有 score 校验之后：

1. 若 `self._active_input` 为空或 contexts 为空：按输入错误处理（fail closed），不静默跳过。
2. 构造 `context_map`。
3. 检查所有 `factual_claim` 的 `evidence_refs`：
   - `unknown_context_id` → 违约；
   - `empty_quote` → 违约；
   - `quote_not_found` → 违约。
4. 若存在违约，抛出 `QuoteContractError(ValueError)`，消息包含（最多前 5 条，总长 ≤ 2000 字符）：
   - `claim_id`、`context_id`、非法 `quote`；
   - `quote_not_found`；
   - 对应 context 原句/窗口；
   - 修复指令：从 contexts 连续复制完整句；不得使用 answer 的加粗句/截断句；找不到连续原文则改判 `insufficient_evidence`。
5. `parse_with_repair` 捕获 `ValueError`，用现有 repair Prompt + `repair_example` 发起 **1 次** repair；不新增重试。
6. repair 后的输出再次走同一校验：
   - 通过 → 返回合法模型；
   - 仍失败 → `StructuredOutputError` → Service `invalid(contract_violation)`，不得静默 drop 或放宽。

`QuoteContractError` 只是 `ValueError` 子类，复用现有 `parse_with_repair` 的捕获路径，不修改 BaseAgent 的重试结构。

### 4.4 记录与追溯（含 invalid 路径）

Agent 增加只读合同报告（不影响计分）：

```python
self.contract_report = {
    "contract_version": "v1.2.3",
    "quote_validator_sha256": "...",
    "quote_precheck_errors": [...],       # 首次校验错误
    "mixed_sentence_warnings": [...],
    "repair_triggered": bool,
    "repair_count": 0 | 1,
    "passed_after_repair": bool | None,
    "final_errors": [...],                # repair 后仍失败时的错误
}
```

**必须覆盖三条路径：**

| 路径 | `agent_contract` 内容 |
|---|---|
| 无 repair，首次通过 | `repair_triggered=false`、`repair_count=0`、`quote_precheck_errors=[]`、`passed_after_repair=true` |
| repair 成功 | 保留首次 `quote_precheck_errors`、`repair_triggered=true`、`repair_count=1`、`passed_after_repair=true` |
| repair 失败 / invalid | 保留首次错误、`repair_count=1`、`passed_after_repair=false`、`final_errors`；**invalid outcome 的 `details.agent_contract` 必须存在**，不能只剩 `structured output is still invalid` |

大小上限：最多 5 条错误；每条 quote ≤ 300 字符、context 句子/窗口 ≤ 300 字符；整个 `agent_contract` ≤ 2000 字符。不要把整段 context 全量塞进 details。

实现位置：

- `RagJudgeAgent` 在 `_validate_parsed` / repair 路径更新 `contract_report`。
- `judge_trace` 在成功和失败两个分支都读取 `getattr(agent, "contract_report", None)`，写入 `details["agent_contract"]`；失败分支必须在构造 `JudgeOutcome` 前读取。
- 仅 v1.2.3 + faithfulness 写该字段；v1.2.0/1/2 的 `details` 不新增该键（或显式为 `None`，测试二选一固定）。

`judge_config` 仅对 v1.2.3 增加：

```text
contract_repair_version = v1.2.3
quote_validator_sha256  = <shared module SHA>
```

v1.2.0/1/2 的 `judge_config` 不得出现这两个键（或显式为 `null`，测试固定口径）。这样报告能同时追溯 Prompt、Agent 合同修复和共享校验代码。

### 4.4.1 上下文一致性（P2）

`neutralize_payload` 在 BaseAgent 中可能改写输入文本；Agent 预校验使用 sanitized input 的 `_active_input.contexts`，Service 使用原始 trace contexts。实现时必须：

- 用 fixture 验证 `neutralize_payload` 前后的 contexts 完全相同（fixture 无注入样文本）；
- 若未来生产 context 可能被改写，预校验应使用与 Service 相同的原始 contexts，或在 `agent_contract` 记录 `contexts_sanitized` 差异；
- 禁止出现“Agent 预校验通过、Service 又判 `quote_not_found`”的静默漂移；出现差异时报告必须可见。

`context_excerpt` 优先返回包含匹配片段的完整句子（按句号/换行切句），而不是固定 ±80 字符；只用于 repair，不参与计分。

### 4.5 为什么这次能闭环

```text
Prompt + contexts
   ↓
模型输出 claims
   ↓
Agent _validate_parsed
   ├─ quote 连续 → 通过
   └─ quote 非连续 → QuoteContractError
                         ↓
              parse_with_repair（1 次）
              + 错误详情 + context 窗口 + repair example
                         ↓
              修复后再次校验
                 ├─ 通过 → Service 复核 → evaluated
                 └─ 失败 → StructuredOutputError → invalid
```

关键差异：**错误发生在 Agent 内部、发生在 repair 之前**；模型能看到 `quote_not_found` 和对应 context 原句。Service 仍用共享校验复核，Agent 不能“自己判自己通过”。

## 5. P0-2：Prompt 证据来源规则

在 v1.2.3 `faithfulness.txt` 增加通用规则（不加 Q23 特例）：

1. `quote` 只能从 `contexts` 复制，不得从 answer 的加粗句、引号句、“根据文档……”转述中复制。
2. `quote` 必须是 context 的连续子串，不得省略句首、从句、连接词、标点。
3. 如果 answer 的表述与 context 不完全一致，以 context 为准，复制完整连续句。
4. 找不到连续原文时判 `insufficient_evidence`，不得截断或改写。
5. 宁可选更短的连续片段，也不得跳过中间字符。
6. 明确反例（通用/合成示例，**不得使用 Q23、生鲜食品或 fixture 原文**）：answer 可写成“商品出现质量问题时可在 24 小时内反馈”，context 原文是“商品签收后不支持无理由退货；出现质量问题的，需在签收后 24 小时内反馈。”；answer 省略了中间的“签收后不支持无理由退货；出现质量问题的”从句，因此不是连续子串。Prompt 只要求“从 context 完整复制”，不得把具体案例写进规则。
7. **防教题约束**：`v1.2.3/faithfulness.txt` 与 repair example 中不得出现 `Q23`、`生鲜食品` 或 Q23 fixture 的完整句子；设计文档可以引用 Q23 作根因说明，但 Prompt 不行。测试必须断言这一点，避免“教到题上”。
8. 修复示例必须同时展示：
   - 一个 `factual_claim` + 完整连续 quote；
   - 一个 `non_factual` + `absence` + `support_status=null` + `evidence_refs=[]`；
   - `reason` 说明“answer 的截断引用不是证据”。

Prompt 规则只负责降低首次错误率；真正闭环靠 P0-1 的预校验/repair。

补充（freeze 阻塞后）：F/C/R 的 few-shot 必须全部去案例化。`m1d5_prompt_leakage_audit.py` 对 10 个 gate case 的 answer/gold/claim/evidence 做 ≥12 字符共享子串审计，findings 必须为 0；Prompt/repair 中不得保留 gate case 的答案句、证据 quote 或期望判断。

## 6. P1：混合句拆分策略

### 6.1 检测

在 v1.2.3 Agent 预校验中增加 clause-level 检测：

- 仅检查 `factual_claim`；
- 识别 absence 标记（“未提及/未说明/未规定/未涉及”等）；
- 要求事实断言与 absence 出现在同一 claim 的分句/整句中；
- `non_factual` + `absence` 不触发；
- 不用关键词直接判分，不用它改写 Service 结果。

### 6.2 策略选择（建议 A）

| 选项 | 行为 | 风险 |
|---|---|---|
| **A（建议）** | `supported` 混合句 → 强制 repair；`insufficient_evidence` 混合句 → warning + 记录，不强制 repair | Q23 cl5 这类 `insufficient` 混合句不会在 v1.2.3 被强制拆分；但不会因 repair 失败把非契约问题升级成 invalid |
| B | 所有混合句都强制 repair | 可能改变 claim 数与 F 分母；repair 失败会把原本可 evaluated 的样本变成 invalid |

选择 A 的理由：用户明确要求“不得为了拆分把非契约问题升级成新的 invalid”。Q23 cl5 是 `insufficient_evidence`，属于软问题；v1.2.3 记录 warning，报告可见，但不强行改判。若人工希望强制拆分，需要在 v1.2.3 审核时明确改为 B，并接受风险。

### 6.3 测试

- `supported` 混合句 → 触发 repair；
- `insufficient` 混合句 → warning，不触发 repair、不 invalid；
- 纯 `non_factual` absence → 不触发；
- 纯 factual（无 absence 标记）→ 不触发；
- 含“未提及”的 context 引用但 claim_type 非 factual → 不误报；
- 不能用 Q23 文本硬编码；用通用正例/反例。

## 10. 测试与静态 validation 计划

### 10.1 共享校验

- 连续 quote → ok；
- 非连续 quote（Q23 answer 截断句）→ `quote_not_found`；
- 错 context → `unknown_context_id`；

## 12. 风险与缓解

| 风险 | 缓解 |
|---|---|
| repair 改变 claim 数/F 分母 | 报告逐 claim 对比；不预写 PASS；以真实结果为准 |
| repair 仍不修复 quote | 第二次失败 → invalid；不放宽、不自动改写 |
| 混合句关键词误报 | clause-level + 正反例；只对 factual、只对 supported 硬修复 |
| Agent/Service 校验漂移 | 共享纯函数 + parity tests + import-linter |
| repair 上下文过长 | 最多 5 条错误、每条 window ≤ 300 字符、error ≤ 2000 字符 |
| 版本回归 | v1.2.0/1/2 行为隔离测试；旧 repair SHA 不变 |
| 成本上升 | 单案例 14 calls / 0.30；10 条 43 calls / 1.00；硬停止 |
| Q21/Q11 仍未验证 | v1.2.3 单案例强制三案例全跑 |

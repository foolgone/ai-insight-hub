## 0. 设计约定

> 本节是全文的口径来源，其他章节与此冲突时以本节为准。

### 0.1 向量维度与索引

| 项 | 取值 |
|---|---|
| 嵌入模型 | `paraphrase-multilingual-MiniLM-L12-v2`（Sentence-Transformers，本地离线） |
| 维度 | **384** |
| 列类型 | `VECTOR(384)` |
| 索引 | **HNSW**（`USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64)`） |
| 相似度算子 | `<=>`（余弦距离） |

> 全库统一 384 维 + HNSW；若历史脚本或旧版本文档给出其他维度/索引类型，以本节为准。

### 0.2 中文全文检索：MVP 用 pg_trgm 降级

`pgvector/pgvector:pg14` 官方镜像**不包含 zhparser**（中文分词扩展），因此：

- **MVP 方案**：`CREATE EXTENSION IF NOT EXISTS pg_trgm;` + `gin (col gin_trgm_ops)` 索引 + `ILIKE '%关键词%'` 查询。
- **zhparser / `to_tsvector('chinese', ...)`**：默认镜像不支持，**MVP 不启用**，SQL 统一收进[附录 A](#附录-a自建-postgresql-镜像预装-zhparser)（自建镜像方案）。
- 扩展清单以 `backend/scripts/init_db.sql` 为准：`vector`、`pg_trgm`、`pgcrypto`。

### 0.3 分区：MVP 采用普通表

> **MVP 采用普通表 + 索引，不分区**。分区方案见[附录 B](#附录-b未来分区方案mvp-未启用)与 [`04-development/11-数据库分区策略调整.md`](../04-development/11-数据库分区策略调整.md)，**未来数据量达标后再启用**。

- 因此 `raw_data` / `cleaned_data` / `audit_logs` 均为普通表，主键分别是 `id`、`id`、`id`（BIGSERIAL），不存在「主键缺分区键」的非法建表。
- 未来启用分区时，`audit_logs` 主键必须写成 `PRIMARY KEY (id, created_at)`，见附录 B。

### 0.4 UUID 与扩展

- UUID 统一用 **内置 `gen_random_uuid()`**（PostgreSQL 13+ 内置，`pgcrypto` 提供同名兼容函数），不再引入第三方 UUID 扩展。
- `init_db.sql` 已声明：`vector`、`pg_trgm`、`pgcrypto`。

## 1. 数据库概述

### 1.1 技术选型

**PostgreSQL 14+ 的优势**：
- ✅ JSONB 支持（灵活存储非结构化数据）
- ✅ 向量扩展（pgvector，HNSW 索引）
- ✅ 模糊检索（pg_trgm；中文分词 zhparser 需自建镜像，MVP 不启用）
- ✅ 行级安全（RLS）
- ✅ 成熟稳定
- ✅ 分区能力可用（**MVP 不启用**，未来数据量达标后按附录 B 演进）

---

### 1.2 数据库规模估算

**假设场景**：中型企业，100 万条对话/月

| 表 | 预估行数（1年） | 单行大小 | 总大小 |
|-----|----------------|----------|--------|
| users | 1,000 | 0.5 KB | 0.5 MB |
| data_sources | 10,000 | 1 KB | 10 MB |
| raw_data | 12M | 2 KB | 24 GB |
| cleaned_data | 12M | 3 KB | 36 GB |
| analysis_results | 12M | 5 KB | 60 GB |
| knowledge_base | 50,000 | 4 KB | 200 MB |
| reports | 10,000 | 0.5 KB | 5 MB |
| **总计** | | | **~120 GB** |

**扩展**：支持 1000 万条对话（10 倍）→ 1.2 TB

## 3. 表结构设计

### 3.1 用户表 (users)

```sql
CREATE TABLE users (
    -- 主键
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- 认证信息
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    
    -- 用户信息
    name VARCHAR(100),
    avatar_url VARCHAR(500),
    
    -- 权限
    role VARCHAR(50) DEFAULT 'user' CHECK (role IN ('admin', 'user', 'viewer')),
    is_active BOOLEAN DEFAULT TRUE,
    is_verified BOOLEAN DEFAULT FALSE,
    
    -- 配额
    quota JSONB DEFAULT '{
        "max_datasources": 10,
        "max_monthly_records": 100000,
        "max_monthly_tokens": 1000000
    }',
    usage JSONB DEFAULT '{
        "datasources_count": 0,
        "monthly_records": 0,
        "monthly_tokens": 0
    }',
    
    -- 时间戳
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    last_login_at TIMESTAMP,
    
    -- 软删除
    deleted_at TIMESTAMP
);

-- 索引
CREATE INDEX idx_users_email ON users(email) WHERE deleted_at IS NULL;
CREATE INDEX idx_users_role ON users(role) WHERE deleted_at IS NULL;
CREATE INDEX idx_users_created_at ON users(created_at);

-- 注释
COMMENT ON TABLE users IS '用户表';
COMMENT ON COLUMN users.quota IS '用户配额限制';
COMMENT ON COLUMN users.usage IS '当前使用情况';
```

### 3.2 数据源表 (data_sources)

```sql
CREATE TABLE data_sources (
    -- 主键
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- 基本信息
    name VARCHAR(255) NOT NULL,
    description TEXT,
    type VARCHAR(50) NOT NULL CHECK (type IN ('customer_service', 'sales', 'support', 'other')),
    
    -- 配置
    config JSONB DEFAULT '{"auto_clean": true, "auto_evaluate": true, "evaluation_dimensions": ["accuracy", "completeness", "tone", "compliance", "hallucination"], "notification_email": "user@example.com"}',
    -- config 默认值说明（evaluation_dimensions 固定 5 维，顺序无关）：
    --   accuracy        准确性
    --   completeness    完整性
    --   tone            语气/礼貌度
    --   compliance      合规性
    --   hallucination   幻觉检测
    
    -- 状态
    status VARCHAR(50) DEFAULT 'active' CHECK (status IN ('active', 'archived', 'processing', 'error')),

    -- 引导流程状态（与 status 是两个维度：status 是生命周期，workflow_status 是引导进度）
    -- 见 docs/04-development/10-知识库冷启动处理.md
    workflow_status VARCHAR(50) DEFAULT 'created' CHECK (
        workflow_status IN ('created', 'data_uploaded', 'data_cleaned', 'knowledge_built', 'ready')
    ),
    
    -- 统计
    statistics JSONB DEFAULT '{
        "total_records": 0,
        "cleaned_records": 0,
        "quality_score_avg": 0,
        "last_processed_at": null
    }',
    
    -- 所属用户
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    
    -- 时间戳
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    deleted_at TIMESTAMP
);

-- 索引
CREATE INDEX idx_datasources_user_id ON data_sources(user_id) WHERE deleted_at IS NULL;
CREATE INDEX idx_datasources_status ON data_sources(status) WHERE deleted_at IS NULL;
CREATE INDEX idx_datasources_type ON data_sources(type) WHERE deleted_at IS NULL;
CREATE INDEX idx_datasources_created_at ON data_sources(created_at);
CREATE INDEX idx_datasources_config ON data_sources USING GIN(config);

-- 注释
COMMENT ON TABLE data_sources IS '数据源表';
COMMENT ON COLUMN data_sources.config IS '数据源配置（JSON）；evaluation_dimensions 默认 5 维';
COMMENT ON COLUMN data_sources.statistics IS '统计信息（JSON）';
```

### 3.3 原始数据表 (raw_data)

**普通表**（MVP 不分区；未来分区写法见附录 B）

```sql
CREATE TABLE raw_data (
    -- 主键
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- 所属数据源
    datasource_id UUID NOT NULL REFERENCES data_sources(id) ON DELETE CASCADE,
    
    -- 原始内容
    raw_content JSONB NOT NULL,
    -- raw_content 示例:
    -- {
    --   "text": "时间: 2025-01-15 10:30\n客户: 你好...",
    --   "format": "csv",
    --   "encoding": "utf-8"
    -- }
    
    -- 文件信息（如果是文件上传）
    file_info JSONB,
    -- file_info 示例:
    -- {
    --   "filename": "data.csv",
    --   "size": 1024000,
    --   "mime_type": "text/csv",
    --   "upload_url": "s3://..."
    -- }
    
    -- 处理状态
    status VARCHAR(50) DEFAULT 'pending' CHECK (status IN ('pending', 'processing', 'completed', 'failed')),
    error_message TEXT,
    
    -- 时间戳
    created_at TIMESTAMP DEFAULT NOW(),
    processed_at TIMESTAMP
);

-- 索引
CREATE INDEX idx_raw_data_datasource_id ON raw_data(datasource_id, created_at DESC);
CREATE INDEX idx_raw_data_status ON raw_data(status);
CREATE INDEX idx_raw_data_created_at ON raw_data(created_at);

-- 注释
COMMENT ON TABLE raw_data IS '原始数据表（MVP 普通表，不分区）';
```

### 3.4 清洗后数据表 (cleaned_data)

**普通表**（MVP 不分区）；向量维度 **384**，索引 **HNSW**；中文检索用 **pg_trgm**。

```sql
CREATE TABLE cleaned_data (
    -- 主键
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- 关联
    datasource_id UUID NOT NULL REFERENCES data_sources(id) ON DELETE CASCADE,
    raw_data_id UUID NOT NULL REFERENCES raw_data(id) ON DELETE CASCADE,  -- T10：数据库外键，raw_data 删除级联清理
    
    -- 结构化数据
    dialogue_id UUID NOT NULL,
    timestamp TIMESTAMP NOT NULL,
    user_message TEXT NOT NULL,
    ai_response TEXT NOT NULL,
    
    -- 元数据
    metadata JSONB DEFAULT '{}',
    -- metadata 示例:
    -- {
    --   "source": "zendesk",
    --   "session_id": "session_123",
    --   "user_id": "customer_123",
    --   "agent_id": "bot_456"
    -- }
    
    -- 质量评分（0-100）
    quality_score FLOAT CHECK (quality_score >= 0 AND quality_score <= 100),
    issues TEXT[],  -- 数组：["missing_timestamp", "short_message"]
    
    -- 向量（384 维，paraphrase-multilingual-MiniLM-L12-v2）
    embedding VECTOR(384),
    
    -- Agent 信息
    agent_version VARCHAR(50),
    processing_duration FLOAT,  -- 秒
    token_usage JSONB,  -- {"input": 100, "output": 200}
    
    -- 时间戳
    created_at TIMESTAMP DEFAULT NOW()
);

-- 索引
CREATE INDEX idx_cleaned_data_datasource_id ON cleaned_data(datasource_id, created_at DESC);
CREATE INDEX idx_cleaned_data_dialogue_id ON cleaned_data(dialogue_id);
CREATE INDEX idx_cleaned_data_timestamp ON cleaned_data(timestamp);
CREATE INDEX idx_cleaned_data_quality_score ON cleaned_data(quality_score);
CREATE INDEX idx_cleaned_data_raw_data_id ON cleaned_data(raw_data_id);

-- 向量索引（HNSW，余弦距离）
CREATE INDEX idx_cleaned_data_embedding ON cleaned_data
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- 中文/模糊检索（MVP：pg_trgm，需先 CREATE EXTENSION pg_trgm）
CREATE INDEX idx_cleaned_data_search ON cleaned_data
    USING GIN ((user_message || ' ' || ai_response) gin_trgm_ops);

-- 查询示例（pg_trgm + ILIKE）
-- SELECT * FROM cleaned_data
-- WHERE user_message ILIKE '%退款%' OR ai_response ILIKE '%退款%'
-- ORDER BY created_at DESC
-- LIMIT 50;

-- 注释
COMMENT ON TABLE cleaned_data IS '清洗后数据表（MVP 普通表，不分区）';
COMMENT ON COLUMN cleaned_data.embedding IS '文本向量表示（384 维，paraphrase-multilingual-MiniLM-L12-v2）';
```

**`raw_data_id` 外键口径（2026-10-26 T10 更新）**：

- **当前（MVP）已建数据库外键**：`cleaned_data.raw_data_id -> raw_data(id) ON DELETE CASCADE`
  （迁移 `007_cleaned_data_raw_data_fk`）。原始数据被删除时级联清理清洗记录，从数据库层消除孤儿行，
  不再依赖应用层自觉；
- 迁移会先清理历史孤儿行再建约束，可重复执行（幂等）；
- **分区演进提示**：若未来启用 `raw_data` 分区（主键变为 `(id, created_at)`），单列外键需随分区方案一并调整；
  届时按 `11-数据库分区策略调整.md` 的演进步骤迁移；
- 巡检 SQL 保留为监控/兜底（正常情况下应为 0 行）：

```sql
-- 巡检：找出孤立记录（有外键后预期恒为 0，用于验证约束确实生效）
SELECT c.id
FROM cleaned_data c
LEFT JOIN raw_data r ON r.id = c.raw_data_id
WHERE r.id IS NULL
LIMIT 100;
```

### 3.5 分析结果表 (analysis_results)

```sql
CREATE TABLE analysis_results (
    -- 主键
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- 关联
    datasource_id UUID NOT NULL REFERENCES data_sources(id) ON DELETE CASCADE,
    data_id UUID NOT NULL,  -- 逻辑外键 -> cleaned_data(id)，理由同 3.4 的 raw_data_id
    
    -- 分析类型
    analysis_type VARCHAR(50) NOT NULL CHECK (
        analysis_type IN ('quality', 'knowledge', 'insight', 'other')
    ),
    
    -- 结果
    result JSONB NOT NULL,
    -- result 示例（质量评估，5 维、0-100）:
    -- {
    --   "overall_score": 85,
    --   "dimensions": {
    --     "accuracy":      {"score": 90, "issues": []},
    --     "completeness":  {"score": 80, "issues": ["incomplete"]},
    --     "tone":          {"score": 88, "issues": []},
    --     "compliance":    {"score": 95, "issues": []},
    --     "hallucination": {"score": 82, "issues": ["price_uncertain"]}
    --   },
    --   "needs_review": false
    -- }
    
    -- Agent 信息
    agent_name VARCHAR(100) NOT NULL,
    agent_version VARCHAR(50),
    ai_model VARCHAR(100),  -- 来自 DEFAULT_LLM_MODEL，默认 deepseek-flash
    
    -- 性能指标
    confidence FLOAT CHECK (confidence >= 0 AND confidence <= 1),
    processing_duration FLOAT,
    token_usage JSONB,
    cost FLOAT,  -- 美元；按实际模型单价计算
    
    -- 时间戳
    created_at TIMESTAMP DEFAULT NOW()
);

-- 索引
CREATE INDEX idx_analysis_datasource_id ON analysis_results(datasource_id, created_at);
CREATE INDEX idx_analysis_data_id ON analysis_results(data_id);
CREATE INDEX idx_analysis_type ON analysis_results(analysis_type);
CREATE INDEX idx_analysis_created_at ON analysis_results(created_at);
CREATE INDEX idx_analysis_result ON analysis_results USING GIN(result);

-- 注释
COMMENT ON TABLE analysis_results IS '分析结果表';
```

> `data_id` 同样按**逻辑外键**处理（同上巡检思路，把 `analysis_results` 左连 `cleaned_data`）。

### 3.6 知识库表 (knowledge_base)

```sql
CREATE TABLE knowledge_base (
    -- 主键
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- 所属数据源
    datasource_id UUID NOT NULL REFERENCES data_sources(id) ON DELETE CASCADE,
    
    -- FAQ 内容
    question TEXT NOT NULL,
    answer TEXT NOT NULL,
    
    -- 分类
    category VARCHAR(100),  -- 产品/售后/咨询等
    tags TEXT[],
    
    -- 统计
    frequency INT DEFAULT 1,  -- 出现次数
    quality_score FLOAT CHECK (quality_score >= 0 AND quality_score <= 100),
    confidence FLOAT CHECK (confidence >= 0 AND confidence <= 1),
    
    -- 来源
    source_dialogue_ids UUID[],
    variations TEXT[],  -- 问题的不同表述
    source VARCHAR(20) DEFAULT 'extracted' CHECK (source IN ('seed', 'manual', 'extracted')),
    is_seed BOOLEAN DEFAULT FALSE,  -- 冷启动种子知识（可被用户数据替换）
    
    -- 向量（384 维，用于相似度检索）
    embedding VECTOR(384),
    
    -- 状态
    status VARCHAR(50) DEFAULT 'active' CHECK (
        status IN ('active', 'archived', 'needs_review')
    ),
    
    -- 时间戳
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    last_used_at TIMESTAMP
);

-- 索引
CREATE INDEX idx_kb_datasource_id ON knowledge_base(datasource_id);
CREATE INDEX idx_kb_category ON knowledge_base(category);
CREATE INDEX idx_kb_frequency ON knowledge_base(frequency DESC);
CREATE INDEX idx_kb_status ON knowledge_base(status);

-- 冷启动相关索引（见 docs/04-development/10-知识库冷启动处理.md）
CREATE INDEX idx_kb_is_seed ON knowledge_base(datasource_id, is_seed);
CREATE INDEX idx_kb_source ON knowledge_base(datasource_id, source);

-- 向量索引（HNSW，与 cleaned_data 保持同一套参数）
CREATE INDEX idx_kb_embedding ON knowledge_base
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- 中文/模糊检索（MVP：pg_trgm）
```

## 4. 索引设计

### 4.1 索引策略

**原则**：
1. 查询频繁的列建索引
2. WHERE/JOIN/ORDER BY 的列建索引
3. 避免过多索引（影响写性能）
4. 定期分析和优化
5. 向量列统一 **HNSW**；中文检索统一 **pg_trgm + GIN**

---

### 4.2 复合索引

```sql
CREATE INDEX IF NOT EXISTS idx_cleaned_data_embedding
```

## 5. 分区策略

### 5.1 MVP 决策：不分区

> **MVP 采用普通表 + 索引，不做分区。** 分区方案见[附录 B](#附录-b未来分区方案mvp-未启用)与 [`04-development/11-数据库分区策略调整.md`](../04-development/11-数据库分区策略调整.md)，**未来数据量达标后再启用**。

**原因**：
- MVP 数据量可控（单表 < 百万级），普通表 + 合适索引即可满足查询；
- 分区需要每月建/删分区，运维负担高，漏建会直接导致插入失败；
- 分区表的主键/唯一约束必须包含分区键，会让 `audit_logs` 等表的主键变成复合主键，牵连外键设计。

**因此本文档 3.3 / 3.4 / 3.10 均为普通表**，不存在「分区表主键缺分区键」的建表错误。

### 5.2 未来启用条件

满足以下**任一**条件时，再按附录 B 启用分区：

- 单表行数 > 5,000 万，且 `created_at` 范围查询占主导；
- 需要按时间批量归档/删除历史数据（如保留 12 个月）；
- `VACUUM` / 索引重建耗时已影响线上维护窗口。

### 5.3 启用步骤（摘要）

1. 按附录 B 的 DDL 新建分区表（`PRIMARY KEY (id, created_at)`）；
2. 用 `INSERT ... SELECT` 分批回灌历史数据；
3. 建立子表索引（父表建索引会自动下发到分区）；
4. 切换应用读写，校验行数与巡检 SQL；
5. 补充每月自动建分区任务（附录 B 的 `create_monthly_partitions`）。

### 7.2 恢复方案

**全量恢复**：

```bash
gunzip -c full_20250115.sql.gz | psql -U aiinsight -h localhost aiinsight
```

**时间点恢复（PITR，PostgreSQL 12+）**：

```bash
# 1. 恢复基础备份到数据目录（先停库）
pg_restore -U aiinsight -d aiinsight base_backup.dump

# 2. 写 PITR 参数：postgresql.conf（不再使用 PG11 及更早的 recovery.conf）
#    restore_command = 'cp /archive/%f %p'
#    recovery_target_time = '2025-01-15 10:30:00'
#    recovery_target_action = 'promote'

# 3. 创建 standby.signal 触发恢复（PG12+ 用信号文件替代 recovery.conf）
touch "$PGDATA/standby.signal"

# 4. 启动数据库，恢复到目标时间后自动 promote
pg_ctl -D "$PGDATA" start
```

> PG12+ 已移除 `recovery.conf`：`restore_command` / `recovery_target_time` 等写入 `postgresql.conf`（或 `postgresql.auto.conf`），恢复触发靠 `standby.signal`。

### B.2 自动建分区

```sql
CREATE OR REPLACE FUNCTION create_monthly_partitions(
    table_name TEXT,
    start_date DATE,
    end_date DATE
)
RETURNS VOID AS $$
DECLARE
    partition_date DATE;
    partition_name TEXT;
    start_range DATE;
    end_range DATE;
BEGIN
    partition_date := DATE_TRUNC('month', start_date)::DATE;
    
    WHILE partition_date < end_date LOOP
        partition_name := table_name || '_' || TO_CHAR(partition_date, 'YYYY_MM');
        start_range := partition_date;
        end_range := (partition_date + INTERVAL '1 month')::DATE;
        
        IF NOT EXISTS (
            SELECT 1 FROM pg_tables WHERE tablename = partition_name
        ) THEN
            EXECUTE format(
                'CREATE TABLE %I PARTITION OF %I FOR VALUES FROM (%L) TO (%L)',
                partition_name, table_name, start_range, end_range
            );
            RAISE NOTICE '创建分区: %', partition_name;
        END IF;
        
        partition_date := (partition_date + INTERVAL '1 month')::DATE;
    END LOOP;
END;
$$ LANGUAGE plpgsql;

-- 使用：创建 2027 年的分区
-- SELECT create_monthly_partitions('raw_data', '2027-01-01', '2028-01-01');
-- SELECT create_monthly_partitions('cleaned_data', '2027-01-01', '2028-01-01');
-- SELECT create_monthly_partitions('audit_logs', '2027-01-01', '2028-01-01');
```

### B.3 自动删除旧分区

```sql
CREATE OR REPLACE FUNCTION drop_old_partitions(
    table_name TEXT,
    retention_months INT
)
RETURNS VOID AS $$
DECLARE
    partition_record RECORD;
    cutoff_date DATE;
    partition_date DATE;
BEGIN
    cutoff_date := (DATE_TRUNC('month', NOW()) - (retention_months || ' months')::INTERVAL)::DATE;
    
    FOR partition_record IN
        SELECT tablename FROM pg_tables
        WHERE tablename LIKE table_name || '\_%'
    LOOP
        partition_date := TO_DATE(
            SUBSTRING(partition_record.tablename FROM '\d{4}_\d{2}$'),
            'YYYY_MM'
        );
        
        IF partition_date < cutoff_date THEN
            EXECUTE format('DROP TABLE %I', partition_record.tablename);
            RAISE NOTICE '删除分区: %', partition_record.tablename;
        END IF;
    END LOOP;
END;
$$ LANGUAGE plpgsql;

-- 使用：删除 12 个月前的分区
-- SELECT drop_old_partitions('raw_data', 12);
```

### B.4 启用分区后必须同步的项

- 主键改为复合主键 → `cleaned_data.raw_data_id` 当前是**单列数据库外键**（T10），分区后需改为带 `created_at` 的复合外键或退回应用层校验；`analysis_results.data_id` 仍为逻辑外键（巡检兜底）；

- 巡检 SQL（3.4 节）仍适用；
- 备份脚本改为「按分区导出 + 保留策略按分区删除」。

# 07 · 参考架构评估（模块化单体 + 异步 Agent Worker）

> 评估对象：外部给出的「模块化单体后端 + 异步 Agent Worker + React 前端 + Docker Compose」参考架构。
> 评估基准：本仓库 `main`（137 个后端源文件 / 645 条测试 / 5 条分层契约全绿）。
> 结论时间：2026-11-11。

## 0. 总体结论

**方向完全一致，不需要重构，只需要补 4 个缺口。**

参考架构主张「不拆微服务、单 FastAPI 应用内部严格分层、Celery 跑 Agent、Compose 编排」——
这正是本仓库已经在跑的结构。逐节对照后：

| 维度 | 一致 | 部分一致 | 缺失 | 不建议采纳 |
| --- | --- | --- | --- | --- |
| 总体架构 / 部署拓扑 | ✅ | | | |

**评分（10 分制）**

## 1. 总体架构与部署拓扑

参考架构：浏览器 → Nginx → FastAPI → PostgreSQL / Redis / MinIO，Celery Worker 独立执行 Agent。

当前实现（`docker-compose.prod.yml`）：

```
nginx / api / worker / beat / postgres(pgvector:pg14) / redis:7 / minio / prometheus / grafana
```

| 参考项 | 当前 | 判定 |
| --- | --- | --- |
| 单体后端 + 独立 worker | api 与 worker 共用同一镜像，仅 command 不同 | ✅ 一致 |
| Nginx 做静态 + 反代 | `nginx/nginx.cloud.conf` + `snippets/aiinsight-locations.conf` | ✅ 一致 |
| 基础设施不暴露公网 | postgres / redis / minio 均无 `ports:` 映射 | ✅ 一致 |
| 可观测 | prometheus + grafana（profile 可选）、`/metrics` 仅内网 | ✅ 超出参考 |

> **不采纳**：拆微服务。当前团队规模与流量不支持，且参考架构本身也建议单体。

## 2. 后端分层

参考分层：

```
api → services → agents → repositories / integrations → models → core
```

当前分层（`backend/app/`，由 `.importlinter` 强制）：

```
api → tasks → services → application → agents → repositories → ports → models → schemas → core
                ↑
         composition（组合根，不在栈内）
```

| 参考项 | 当前实现 | 判定 |
| --- | --- | --- |
| `api/` 只做 HTTP | 路由 + JWT/RBAC + BYOK 守门 + 分页参数解析 | ✅ |
| `services/` 业务服务 | 20 个 service，持有事务边界（`flush`） | ✅ |
| `agents/` 编排与具体 Agent | `BaseAgent` + 6 个能力（cleaning/structure/evaluation/extraction/insight/report） | ✅ |
| `tasks/` Celery 任务 | 7 个任务，纯转发（不持业务逻辑） | ✅ |
| `repositories/` 数据访问 | 4 张热点表 + 分页执行（`cleaned_data` / `knowledge_base` / `analysis_results` / `raw_data`） | ⚠️ 部分（`Task` / `DataSource` / `Report` 仍在 service 里） |
| `integrations/` 外部适配器 | 我们用 `ports/`（Protocol）+ `services/*`（实现），更严格 | ✅ 等价且更强 |
| `core/` 配置鉴权日志异常 | 20 个模块 | ✅ |
| 路由不直接操作数据库 | CI grep 门禁：`api` / `application` 禁止 `session.add/delete` | ✅ 超出参考 |
| Agent 不依赖 HTTP 对象 | Agent 只接收 `input_data` / `session` / `user_id` | ✅ |

**关键差异：`integrations/` vs `ports/`**

参考架构把 LLM/MinIO/Redis 适配器放在 `integrations/`，业务直接 import。
我们额外定义了 `ports/`（`LLMPort` / `TranscriberPort` / `CredentialPort`），
业务依赖 Protocol，实现放在 service 侧。**这是参考架构没有、但更利于替换与测试的一层**，建议保留。

## 3. Agent 运行方式

参考：同步查询走 API，异步 Agent 走 Celery，统一 `BaseAgent.run(context)`，统一记录
`task_id / status / progress / tokens / cost / error / 起止时间`。

| 参考项 | 当前 | 判定 |
| --- | --- | --- |
| 同步查询直连 DB | ✅ | ✅ |
| 异步任务经 Redis → Worker | ✅（broker DB1，result DB2） | ✅ |
| 统一 Agent 接口 | `BaseAgent.invoke(input_data, *, session, task_id, scope, user_id, datasource_id)` | ✅ 等价（`run(context)` 的语义已覆盖） |
| 统一任务字段 | `tasks`：`status / progress / current_step / result / error_message / started_at / completed_at / duration / retry_count / celery_task_id` | ⚠️ 缺 tokens/cost 聚合 |
| 成本审计 | 独立 `llm_calls` 表（含 `key_source` 区分 BYOK/服务端） | ✅ 更细，但未回填到 task |
| 进度推送 | SSE `/api/v1/tasks/stream`，1s 轮询 PG 快照 | ✅ |

**建议补齐（P1，2h）**：`tasks.result` 里已有 `token_usage` 等字段的业务任务可聚合，
但通用任务表没有 `input_tokens / output_tokens / cost` 三列。补三列 + 在 `_track_success` 回填，
前端任务列表可直接显示成本，不必再 join `llm_calls`。

## 4. PostgreSQL + pgvector

参考：业务表与向量表逻辑分离、HNSW 索引、固定 embedding 模型与维度（384）。

| 参考项 | 当前 | 判定 |
| --- | --- | --- |
| 业务 + 向量同一 PG | ✅ `pgvector/pgvector:pg14` | ✅ |
| 固定维度 384 | `Vector(dim=384)`，模型 `paraphrase-multilingual-MiniLM-L12-v2` | ✅ |
| HNSW 索引 | `idx_cleaned_data_embedding` / `idx_kb_embedding`，`m=16, ef_construction=64, vector_cosine_ops` | ✅ 已按最佳实践建 |
| 向量与业务表分离 | 我们采用「同表加列」（`cleaned_data.embedding`、`knowledge_base.embedding`） | ⚠️ 不同但合理 |

**关于「同表加列」的说明**：参考架构建议独立 `*_embeddings` 表。当前做法在 384 维、
数据量万级时更简单（少一次 join，事务一致），且已有 HNSW 索引。**不建议为对齐参考而拆表**；
当单个业务表向量超过百万级、或需要多模型并存时再拆。

## 5. Redis 职责拆分

参考：DB0 缓存/会话/限流，DB1 Broker，DB2 Result，DB3 任务进度/SSE 状态。

| 参考项 | 当前 | 判定 |
| --- | --- | --- |
| DB0 缓存 / 限流 / token 黑名单 | `REDIS_URL=redis://.../0` | ✅ |
| DB1 Celery Broker | `CELERY_BROKER_URL=.../1` | ✅ |
| DB2 Celery Result | `CELERY_RESULT_BACKEND=.../2` | ✅ |
| DB3 任务进度 / SSE 状态 | 未使用：进度存在 PG `tasks.current_step/progress` | ✅ 更优 |

**不建议采纳 DB3**：进度若写 Redis，会与 PG 形成双写，任务崩溃时两者不一致；
现在 SSE 直接读 PG 快照（1s 轮询），正确性由单一事实源保证，代价只是一点查询压力。

## 6. MinIO 职责

参考：5 个 bucket（uploads / cleaned / reports / exports / temp），元数据存 PG，用短期预签名 URL。

| 参考项 | 当前 | 判定 |
| --- | --- | --- |
| 原始文件桶 | `aiinsight-uploads` | ✅ |
| 报告桶 | `aiinsight-reports` | ✅ |
| cleaned / exports / temp 桶 | 未拆（清洗结果直接入库，无中间文件；导出走报告桶） | ✅ 无需拆 |
| 元数据存 PG | `raw_data.file_info`（object_name / size / mime / backend）+ `reports` 表 | ✅ |
| 文件内容不入库 | ✅ | ✅ |
| 预签名 URL | 报告下载走 API 代理（`GET /reports/{id}/download` 流式返回，鉴权在 API） | ✅ 等价 |
| 本地回退 | `STORAGE_BACKEND=auto`，MinIO 不可用回退 `.storage/` | ✅ 超出参考 |

**关于预签名**：参考架构的目的是「不让浏览器直连对象存储、不暴露永久 URL」。
我们用「后端代理下载 + 鉴权」达成同样效果，且不必把 MinIO 暴露到公网。
需要修的一处：`raw_data.file_info.upload_url` 存的是内部地址（`http://minio:9000/<bucket>/<object>`），
且会随上传响应返回给前端（`app/schemas/processing.py` 的 `FileInfo.upload_url`）。前端并未使用它，
但这是无必要的信息暴露（内网主机名 + 桶结构）。建议上传响应不再返回该字段，或改返回后端下载路径
（需新增 `/api/v1/datasources/{id}/raw-data/{raw_id}/download` 端点）。

## 8. 生产部署

| 参考项 | 当前 | 判定 |
| --- | --- | --- |
| 服务划分 | nginx / api / worker / beat / postgres / redis / minio（+ monitoring） | ✅ |
| `/` 静态、`/api` 反代 | ✅ | ✅ |
| `/docs` 限制访问 | ✅ 已限制内网（`afa7f1e`） | ✅ |
| `/files` 临时下载 | 报告下载走 `/api/v1/reports/{id}/download` | ✅ 等价 |
| 基础设施不暴露公网 | ✅ | ✅ |
| api/worker/beat 同镜像 | ✅ | ✅ |
| Worker 独立扩容 `--scale worker=3` | 未启用（单机 `concurrency=2`） | ⚠️ 受内存约束 |
| 多队列（clean/evaluate/embedding/report） | 仅 `clean` / `default` | ⚠️ 部分 |
| 密码/JWT/Key 不入库 | ✅ `.env` + GitHub Secrets | ✅ |
| 备份 | ✅ 脚本 + 每日 crontab + 恢复演练（2026-11-11）；⚠️ 未配离机副本 | ✅ 可接受，需补 `OFFSITE_DIR` |

**关于 `--scale worker=3`**：云服务器 1.9GB 内存 / 2 核，单个 worker（concurrency=2 + 嵌入模型）
已接近上限，扩到 3 个会 OOM。VM（7.5GB / 4 核）可以，但当前无此需求。
**建议：先不横向扩容，改为「按队列隔离 + 超时保护」**（已做：`clean` 独立队列、`acks_late`、
`visibility_timeout=3600`）。

**关于多队列**：参考建议按业务拆 5 个队列。当前只有「长任务（clean）/ 短任务（default）」两类，
再拆会让单机 worker 的消费配置变复杂而收益有限。**触发条件**：当向量生成或报告生成
单次超过 5 分钟、开始阻塞短任务时，再拆 `embedding` / `report` 队列。

## 12. 一句话总结

**参考架构是「该怎么做」的正确方向，本仓库是「已经这么做、并且在分层与可靠性上更进一步」的实现。
2026-11-11 起，原先的两个运维缺口（`/docs` 暴露、无备份演练）已分别由 `afa7f1e` 与 `ops/backup/` 关闭；
剩余的是「备份未配离机副本」这一项必须补，以及两个可选优化（任务成本字段、前端 features 收口），
不需要任何结构性重构。**

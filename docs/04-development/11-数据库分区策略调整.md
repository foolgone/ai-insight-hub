## 1. 问题描述

### 1.1 历史方案（已过时）

- `raw_data` - 原始数据表
- `cleaned_data` - 清洗后数据表

### 1.3 不分区的代价

❌ **运维负担**（若启用分区）：
- 需要定期创建新分区（每月）
- 需要定期删除旧分区
- 忘记创建分区 → 数据插入失败

❌ **过早优化**：
- MVP 数据量远低于分区阈值
- 查询模式简单，普通索引足够

❌ **增加复杂度**：
- 查询需要考虑分区裁剪
- 备份恢复更复杂
- 索引管理更复杂

## 2. 分区策略对比

### 2.1 不分区 vs 分区

| 维度 | 不分区 | 按月分区 |
|------|--------|----------|
| **查询性能** | 全表扫描 | 只扫描相关分区 ⭐ |
| **插入性能** | 快 | 稍慢（路由分区） |
| **维护** | 简单 ⭐ | 复杂（需要管理分区） |
| **数据清理** | DELETE 慢 | DROP 分区快 ⭐ |
| **适用数据量** | < 1000 万 | ≥ 1000 万 ⭐ |
| **初期成本** | 低 ⭐ | 高（需要自动化） |

---

### 2.2 何时需要分区？

> **统一阈值**：`数据量 ≥ 1000 万行` 才考虑分区。全项目（本文、`03-数据库设计.md`、`04-开发方案.md`）使用同一口径，不再出现 100 万 / 80 万等旧阈值。

**✅ 需要分区的场景**：
- 单表数据量 **≥ 1000 万行**
- 频繁按时间范围查询（如「查询最近 7 天」）
- 需要定期删除旧数据
- 数据库性能瓶颈已出现，且索引/查询优化已做过

**❌ 不需要分区的场景**：
- 数据量 **< 1000 万行**（MVP 与早期生产阶段）
- 查询模式简单
- 不需要删除旧数据
- 团队缺少 DBA 经验

## 3. 推荐方案

### 3.1 阶段性策略

```
Phase 1 (MVP, 0-6个月)
├─ 不使用分区
├─ 数据量预估 < 100 万
└─ 关注功能开发

Phase 2 (生产, 6-12个月)
├─ 观察数据量增长
├─ 单表接近 1000 万时启动评估
└─ 做迁移演练（不切线上）

Phase 3 (规模化, 数据量 >= 1000 万)
├─ 启用分区
└─ 使用自动化工具（pg_partman）
```

---

### 3.2 具体建议

#### **MVP 阶段（推荐）**

**不使用分区，使用普通表**：

```sql
-- ✅ 简化版（不分区）
CREATE TABLE raw_data (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    datasource_id UUID NOT NULL REFERENCES data_sources(id) ON DELETE CASCADE,
    raw_content JSONB NOT NULL,
    file_info JSONB,
    status VARCHAR(50) DEFAULT 'pending',
    error_message TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    processed_at TIMESTAMP
);

-- 索引（重点）
CREATE INDEX idx_raw_data_datasource_created 
    ON raw_data(datasource_id, created_at DESC);
CREATE INDEX idx_raw_data_status 
    ON raw_data(status, created_at DESC);
CREATE INDEX idx_raw_data_created 
    ON raw_data(created_at DESC);

-- 定期清理（可选）
CREATE OR REPLACE FUNCTION cleanup_old_raw_data()
RETURNS void AS $$
BEGIN
    DELETE FROM raw_data
    WHERE created_at < NOW() - INTERVAL '6 months'
      AND status = 'completed';
END;
$$ LANGUAGE plpgsql;

-- 定时任务（每周执行）
-- 使用 pg_cron 或 Celery Beat
```

**优点**：
- ✅ 简单，无需管理分区
- ✅ 查询性能在 1000 万行以内通常够用（需实测）
- ✅ 降低开发和运维成本

**缺点**：
- ⚠️ 数据量 ≥ 1000 万时性能下降
- ⚠️ 删除旧数据较慢（需要 VACUUM）

---

#### **生产阶段（数据量 ≥ 1000 万）**

**使用 pg_partman 自动管理分区**：

```sql
-- 1. 安装 pg_partman 扩展
CREATE EXTENSION pg_partman;

-- 2. 创建分区表（使用 pg_partman）
SELECT partman.create_parent(
    p_parent_table := 'public.raw_data',
    p_control := 'created_at',
    p_type := 'native',
    p_interval := 'monthly',
    p_premake := 3,              -- 提前创建 3 个月的分区
    p_start_partition := '2026-01-01'
);

-- 3. 自动维护（每天运行）
SELECT partman.run_maintenance_proc();

-- 4. 自动删除旧分区（保留 6 个月）
UPDATE partman.part_config
SET retention = '6 months',
    retention_keep_table = false
WHERE parent_table = 'public.raw_data';
```

**优点**：
- ✅ 自动创建分区（无需手动）
- ✅ 自动删除旧分区（无需手动）
- ✅ 查询性能大幅提升
- ✅ 删除旧数据快（DROP 分区）

**缺点**：
- ⚠️ 需要安装和配置 pg_partman
- ⚠️ 略微增加复杂度

## 4. 实施指南

### 4.1 MVP 阶段实施

#### Step 1: 修改数据库设计文档

**移除分区表定义**，使用普通表：

```sql
-- 修改前（分区表）——仅作对照，MVP 不启用
-- CREATE TABLE raw_data (...) PARTITION BY RANGE (created_at);
-- CREATE TABLE raw_data_2026_10 PARTITION OF raw_data
--     FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

-- 修改后（普通表）
CREATE TABLE raw_data (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    datasource_id UUID NOT NULL,
    raw_content JSONB NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

-- 重点：创建高效索引
CREATE INDEX idx_raw_data_datasource_created
    ON raw_data(datasource_id, created_at DESC);
```

> 上面「普通表」只列关键字段，完整字段见 `docs/03-architecture/03-数据库设计.md` §3.3。

---

#### Step 2: 数据清理策略

**定期清理旧数据**（可选）：

```python
# app/tasks/cleanup.py
import asyncio

from celery import Celery
from celery.schedules import crontab
from loguru import logger

from app.core.db import get_db

celery_app = Celery("aiinsight")


@celery_app.task
def cleanup_old_data():
    """清理 6 个月前的已处理数据

    Celery worker 是同步进程，异步逻辑用 asyncio.run 驱动；
    不要给 task 直接加 async def。
    """
    asyncio.run(_cleanup_old_data_async())


async def _cleanup_old_data_async():
    db = get_db()

    # 1. 清理原始数据
    deleted = await db.execute(
        """
        DELETE FROM raw_data
        WHERE created_at < NOW() - INTERVAL '6 months'
          AND status = 'completed'
        """
    )
    logger.bind(table="raw_data", deleted=deleted).info("cleanup_old_data_done")

    # 2. 清理审计日志（保留 3 个月）
    deleted_audit = await db.execute(
        """
        DELETE FROM audit_logs
        WHERE created_at < NOW() - INTERVAL '3 months'
        """
    )
    logger.bind(table="audit_logs", deleted=deleted_audit).info(
        "cleanup_audit_logs_done"
    )

    # 3. VACUUM 不能在事务块里执行，必须用 autocommit 连接单独跑
    async with db.autocommit() as conn:
        await conn.execute("VACUUM ANALYZE raw_data")
        await conn.execute("VACUUM ANALYZE audit_logs")


# Celery Beat 配置（每周日凌晨执行）
celery_app.conf.beat_schedule = {
    "cleanup-old-data": {
        "task": "app.tasks.cleanup.cleanup_old_data",
        "schedule": crontab(hour=2, minute=0, day_of_week=0),
    }
}
```

> ⚠️ `VACUUM` 不能在事务中运行。如果你的数据库封装没有 `autocommit()`，改用 `asyncpg` 的 `connection.execute` 并确保连接 `autocommit=True`；或者交给 `pg_cron` / 运维脚本执行。

#### Step 3: 监控数据量

**设置监控指标**，提前预警：

```python
# app/monitoring/metrics.py
from loguru import logger
from prometheus_client import Gauge

# 数据量监控
table_row_count = Gauge(
    "table_row_count",
    "Number of rows in table",
    ["table_name"],
)

# 分区评估阈值：1000 万行；达到 80% 时提前预警
PARTITION_THRESHOLD = 10_000_000
PARTITION_WARN_AT = int(PARTITION_THRESHOLD * 0.8)  # 800 万

# 白名单：表名不能来自外部输入
MONITORED_TABLES = ("raw_data", "cleaned_data", "analysis_results")


async def update_table_metrics(db):
    """更新表行数指标"""

    for table in MONITORED_TABLES:
        # 表名来自上面的白名单，可安全拼接；不要传入用户可控值
        count = await db.fetch_val(f"SELECT COUNT(*) FROM {table}")
        count = int(count or 0)

        table_row_count.labels(table_name=table).set(count)

        if count >= PARTITION_WARN_AT:
            logger.bind(table=table, rows=count).warning(
                "table_row_count_near_partition_threshold"
            )
```

> `COUNT(*)` 在大表上开销高，生产环境建议改为 `pg_class.reltuples` 估算，或每天低峰期跑一次。

### 4.2 迁移到分区表（未来）

**当数据量接近 1000 万时**：

```python
# scripts/migrate_to_partitioned_table.py
"""
迁移普通表到分区表

警告：需要停机维护，请在低峰期执行。
执行前必须：备份全库、在预发环境完整演练、确认没有长事务。
"""

from datetime import datetime, timedelta

from loguru import logger


async def migrate_to_partitioned(db):
    """迁移到分区表（raw_data 示例）"""

    # 1. 创建新的分区表（INCLUDING ALL 会带上索引/约束/默认值）
    await db.execute(
        """
        CREATE TABLE raw_data_new (
            LIKE raw_data INCLUDING ALL
        ) PARTITION BY RANGE (created_at);
        """
    )

    # 2. 按自然月建分区：从最早数据所在月建到「下个月」
    earliest = await db.fetch_val("SELECT MIN(created_at) FROM raw_data")
    start = (earliest or datetime.now()).replace(
        day=1, hour=0, minute=0, second=0, microsecond=0
    )
    end = (datetime.now() + timedelta(days=62)).replace(
        day=1, hour=0, minute=0, second=0, microsecond=0
    )

    cursor = start
    while cursor < end:
        next_month = (cursor.replace(day=28) + timedelta(days=4)).replace(day=1)
        partition_name = f"raw_data_{cursor.strftime('%Y_%m')}"
        await db.execute(
            f"""
            CREATE TABLE IF NOT EXISTS {partition_name}
            PARTITION OF raw_data_new
            FOR VALUES FROM ('{cursor:%Y-%m-%d}') TO ('{next_month:%Y-%m-%d}');
            """
        )
        cursor = next_month

    # 2.1 兜底分区：承接范围外/异常时间戳，避免插入直接报错
    await db.execute(
        "CREATE TABLE IF NOT EXISTS raw_data_default PARTITION OF raw_data_new DEFAULT;"
    )

    # 3. 复制数据
    await db.execute("INSERT INTO raw_data_new SELECT * FROM raw_data;")

    # 4. 校验行数（复制完成、切换前）
    old_count = await db.fetch_val("SELECT COUNT(*) FROM raw_data")
    new_count = await db.fetch_val("SELECT COUNT(*) FROM raw_data_new")
    if old_count != new_count:
        raise RuntimeError(f"行数不一致：old={old_count}, new={new_count}")

    # 5. 交换表名（需要停机；建议在单事务内完成）
    await db.execute("ALTER TABLE raw_data RENAME TO raw_data_old;")
    await db.execute("ALTER TABLE raw_data_new RENAME TO raw_data;")

    logger.bind(old=old_count, new=new_count).info("partition_migration_done")

    # 6. 观察 1-2 周后再删旧表
    # await db.execute("DROP TABLE raw_data_old;")
```

> ⚠️ 迁移注意：
> - `LIKE ... INCLUDING ALL` **不会**复制外键，若其他表引用 `raw_data`，需手工重建；
> - 主键/唯一约束必须包含分区键 `created_at`，否则建表会失败（与 `03-数据库设计.md` 附录 B 一致）；
> - 切换表名后要重新 `ANALYZE`，否则执行计划可能走错；
> - 应用侧连接池需重连，避免持有旧表的元数据缓存。

## 📊 决策矩阵

### 当前数据量 < 800 万条

**推荐**：❌ **不使用分区**

**理由**：
- 简单优先
- 性能足够
- 避免过早优化

---

### 当前数据量 800 万 - 1000 万条

**推荐**：⚠️ **观察和评估**

**行动**：
- 监控查询性能（P95）
- 监控数据增长速度
- 在预发环境演练迁移

---

### 当前数据量 ≥ 1000 万条

**推荐**：✅ **启用分区（使用 pg_partman）**

**理由**：
- 查询性能提升明显
- 数据清理更快
- 自动化管理降低运维负担

---

## ✅ 最终建议

### **MVP 阶段（当前）**

**不使用分区**，理由：

1. ✅ **简化开发**：专注功能，不被基础设施分心
2. ✅ **降低风险**：减少运维复杂度
3. ✅ **性能足够**：1000 万行以内通常够用（需实测）
4. ✅ **成本更低**：无需投入分区管理

### **生产阶段（未来）**

当满足以下**任一条件**时，启用分区：

- 📊 单表数据量 **≥ 1000 万行**
- 🐌 查询明显变慢（P95 > 2 秒），且索引/查询优化已做过
- 🗑️ 需要定期删除旧数据（按月归档）
- 💰 有专职 DBA 或运维

### **工具选择**

- 手动分区：❌ 不推荐（运维负担重）
- **pg_partman**：✅ 强烈推荐（自动化）
- TimescaleDB：⏸️ 如果主要是时序数据可考虑

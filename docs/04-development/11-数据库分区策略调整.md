## 1. 问题描述

### 当前设计

在数据库设计中，对以下表使用了**按月分区**：
- `raw_data` - 原始数据表
- `cleaned_data` - 清洗后数据表
- `audit_logs` - 审计日志表

### 存在的问题

❌ **运维负担**：
- 需要定期创建新分区（每月）
- 需要定期删除旧分区
- 忘记创建分区 → 数据插入失败

❌ **MVP 阶段可能不需要**：
- 数据量可能不大（< 10万条）
- 过早优化

❌ **增加复杂度**：
- 查询需要考虑分区
- 备份恢复更复杂
- 索引管理更复杂

---

## 2. 分区策略对比

### 2.1 不分区 vs 分区

| 维度 | 不分区 | 按月分区 |
|------|--------|----------|
| **查询性能** | 全表扫描 | 只扫描相关分区 ⭐ |
| **插入性能** | 快 | 稍慢（路由分区） |
| **维护** | 简单 ⭐ | 复杂（需要管理分区） |
| **数据清理** | DELETE 慢 | DROP 分区快 ⭐ |
| **适用数据量** | < 100万 | > 100万 ⭐ |
| **初期成本** | 低 ⭐ | 高（需要自动化） |

---

### 2.2 何时需要分区？

**✅ 需要分区的场景**：
- 数据量 > **100万行**
- 频繁按时间范围查询（如"查询最近7天"）
- 需要定期删除旧数据
- 数据库性能瓶颈已出现

**❌ 不需要分区的场景**：
- 数据量 < **10万行**（MVP 阶段）
- 查询模式简单
- 不需要删除旧数据
- 团队缺少 DBA 经验

## 3. 推荐方案

### 3.1 阶段性策略

```
Phase 1 (MVP, 0-6个月)
├─ 不使用分区
├─ 数据量预估 < 50万
└─ 关注功能开发

Phase 2 (生产, 6-12个月)
├─ 观察数据量增长
├─ 当数据量接近 100万时
└─ 评估是否需要分区

Phase 3 (规模化, 12个月+)
├─ 数据量 > 100万
├─ 启用分区
└─ 使用自动化工具（pg_partman）
```

---

### 3.2 具体建议

#### **MVP 阶段（推荐）**

**不使用分区，使用普通表**：

```sql
-- ✅ 简化版（不分区）
CREATE TABLE raw_data (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    datasource_id UUID NOT NULL REFERENCES data_sources(id) ON DELETE CASCADE,
    raw_content JSONB NOT NULL,
    file_info JSONB,
    status VARCHAR(50) DEFAULT 'pending',
    error_message TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    processed_at TIMESTAMP
);

-- 索引（重点）
CREATE INDEX idx_raw_data_datasource_created 
    ON raw_data(datasource_id, created_at DESC);
CREATE INDEX idx_raw_data_status 
    ON raw_data(status, created_at DESC);
CREATE INDEX idx_raw_data_created 
    ON raw_data(created_at DESC);

-- 定期清理（可选）
CREATE OR REPLACE FUNCTION cleanup_old_raw_data()
RETURNS void AS $$
BEGIN
    DELETE FROM raw_data
    WHERE created_at < NOW() - INTERVAL '6 months'
      AND status = 'completed';
END;
$$ LANGUAGE plpgsql;

-- 定时任务（每周执行）
-- 使用 pg_cron 或 Celery Beat
```

**优点**：
- ✅ 简单，无需管理分区
- ✅ 查询性能在 100万以内完全够用
- ✅ 降低开发和运维成本

**缺点**：
- ⚠️ 数据量 > 100万时性能下降
- ⚠️ 删除旧数据较慢（需要 VACUUM）

---

#### **生产阶段（数据量 > 100万）**

**使用 pg_partman 自动管理分区**：

```sql
-- 1. 安装 pg_partman 扩展
CREATE EXTENSION pg_partman;

-- 2. 创建分区表（使用 pg_partman）
SELECT partman.create_parent(
    p_parent_table := 'public.raw_data',
    p_control := 'created_at',
    p_type := 'native',
    p_interval := 'monthly',
    p_premake := 3,              -- 提前创建 3 个月的分区
    p_start_partition := '2026-01-01'
);

-- 3. 自动维护（每天运行）
SELECT partman.run_maintenance_proc();

-- 4. 自动删除旧分区（保留 6 个月）
UPDATE partman.part_config
SET retention = '6 months',
    retention_keep_table = false
WHERE parent_table = 'public.raw_data';
```

**优点**：
- ✅ 自动创建分区（无需手动）
- ✅ 自动删除旧分区（无需手动）
- ✅ 查询性能大幅提升
- ✅ 删除旧数据快（DROP 分区）

**缺点**：
- ⚠️ 需要安装和配置 pg_partman
- ⚠️ 略微增加复杂度

## 4. 实施指南

### 4.1 MVP 阶段实施

#### Step 1: 修改数据库设计文档

**移除分区表定义**，使用普通表：

```sql
-- 修改前（分区表）
CREATE TABLE raw_data (...) PARTITION BY RANGE (created_at);
CREATE TABLE raw_data_2026_10 PARTITION OF raw_data ...;

-- 修改后（普通表）
CREATE TABLE raw_data (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    datasource_id UUID NOT NULL,
    raw_content JSONB NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    ...
);

-- 重点：创建高效索引
CREATE INDEX idx_raw_data_datasource_created 
    ON raw_data(datasource_id, created_at DESC);
```

---

#### Step 2: 数据清理策略

**定期清理旧数据**（可选）：

```python
# app/tasks/cleanup.py
from celery import Celery

celery_app = Celery("ai_insight_hub")

@celery_app.task
async def cleanup_old_data():
    """清理 6 个月前的已处理数据"""
    
    # 1. 清理原始数据
    result = await db.execute(
        """
        DELETE FROM raw_data
        WHERE created_at < NOW() - INTERVAL '6 months'
          AND status = 'completed'
        """
    )
    
    logger.info(f"Cleaned {result} old raw_data records")
    
    # 2. VACUUM（回收空间）
    await db.execute("VACUUM ANALYZE raw_data")
    
    # 3. 清理审计日志（保留 3 个月）
    await db.execute(
        """
        DELETE FROM audit_logs
        WHERE created_at < NOW() - INTERVAL '3 months'
        """
    )
    
    await db.execute("VACUUM ANALYZE audit_logs")

# Celery Beat 配置（每周日凌晨执行）
celery_app.conf.beat_schedule = {
    "cleanup-old-data": {
        "task": "app.tasks.cleanup.cleanup_old_data",
        "schedule": crontab(hour=2, minute=0, day_of_week=0),
    }
}
```

#### Step 3: 监控数据量

**设置监控指标**，提前预警：

```python
# app/monitoring/metrics.py
from prometheus_client import Gauge

# 数据量监控
table_row_count = Gauge(
    'table_row_count',
    'Number of rows in table',
    ['table_name']
)

async def update_table_metrics():
    """更新表行数指标"""
    
    tables = ['raw_data', 'cleaned_data', 'analysis_results']
    
    for table in tables:
        count = await db.fetch_val(
            f"SELECT COUNT(*) FROM {table}"
        )
        
        table_row_count.labels(table_name=table).set(count)
        
        # 告警：超过 80万行
        if count > 800_000:
            logger.warning(
                f"Table {table} has {count:,} rows, "
                f"consider enabling partitioning"
            )
```

### 4.2 迁移到分区表（未来）

**当数据量接近 100万时**：

```python
# scripts/migrate_to_partitioned_table.py
"""
迁移普通表到分区表

警告：需要停机维护，请在低峰期执行
"""

async def migrate_to_partitioned():
    """迁移到分区表"""
    
    # 1. 创建新的分区表
    await db.execute("""
        CREATE TABLE raw_data_new (
            LIKE raw_data INCLUDING ALL
        ) PARTITION BY RANGE (created_at);
    """)
    
    # 2. 创建分区（最近 6 个月）
    for i in range(6):
        month_start = datetime.now() - timedelta(days=30*i)
        month_end = month_start + timedelta(days=30)
        
        partition_name = f"raw_data_{month_start.strftime('%Y_%m')}"
        
        await db.execute(f"""
            CREATE TABLE {partition_name}
            PARTITION OF raw_data_new
            FOR VALUES FROM ('{month_start}') TO ('{month_end}');
        """)
    
    # 3. 复制数据
    await db.execute("""
        INSERT INTO raw_data_new
        SELECT * FROM raw_data;
    """)
    
    # 4. 交换表名（需要停机）
    await db.execute("ALTER TABLE raw_data RENAME TO raw_data_old;")
    await db.execute("ALTER TABLE raw_data_new RENAME TO raw_data;")
    
    # 5. 验证数据
    old_count = await db.fetch_val("SELECT COUNT(*) FROM raw_data_old")
    new_count = await db.fetch_val("SELECT COUNT(*) FROM raw_data")
    
    assert old_count == new_count, "Data count mismatch!"
    
    # 6. 删除旧表（确认无误后）
    # await db.execute("DROP TABLE raw_data_old;")
    
    print("Migration completed!")
```

## 📊 决策矩阵

### 当前数据量 < 10万条

**推荐**：❌ **不使用分区**

**理由**：
- 简单优先
- 性能足够
- 避免过早优化

---

### 当前数据量 10万 - 100万条

**推荐**：⚠️ **观察和评估**

**行动**：
- 监控查询性能
- 监控数据增长速度
- 做好分区迁移准备

---

### 当前数据量 > 100万条

**推荐**：✅ **启用分区（使用 pg_partman）**

**理由**：
- 查询性能提升明显
- 数据清理更快
- 自动化管理降低运维负担

---

## ✅ 最终建议

### **MVP 阶段（当前）**

**不使用分区**，理由：

1. ✅ **简化开发**：专注功能，不被基础设施分心
2. ✅ **降低风险**：减少运维复杂度
3. ✅ **性能足够**：100万以内性能完全够用
4. ✅ **成本更低**：无需投入分区管理

### **生产阶段（未来）**

当满足以下**任一条件**时，启用分区：

- 📊 数据量 > **100万行**
- 🐌 查询明显变慢（> 2秒）
- 🗑️ 需要定期删除旧数据
- 💰 有专职 DBA 或运维

### **工具选择**

- 手动分区：❌ 不推荐（运维负担重）
- **pg_partman**：✅ 强烈推荐（自动化）
- TimescaleDB：⏸️ 如果主要是时序数据可考虑

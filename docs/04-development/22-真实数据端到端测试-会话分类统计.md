## 三、发现的问题

### 已修复（随 PR #38）

| # | 问题 | 影响 |
| --- | --- | --- |
| 1 | 清洗入口给 `agent.clean()` 误传 `credentials=` | **任何文本清洗任务 5% 立即失败**（线上自 11-12 起全挂） |
| 2 | 推理模型输出被 `max_tokens=4096` 截断 | 50 行 CSV 即触发 `finish_reason=length` → `no dialogues` |
| 3 | `normalize_text` 把换行压成空格 | 51 行 CSV 变 1 行，模型只能靠逗号猜结构 |
| 4 | CSV 列数与表头不一致时**静默入库** | `可沉淀知识_300.csv`（表头 6 列 / 数据 7 列）清洗出 20 条，但 `ai_response` 被写成「知识类,客户反馈…」——错位数据比失败更危险。现改为 415 并提示第几行、差几列 |

### 待修（按影响排序）

| # | 问题 | 建议 |
| --- | --- | --- |
| 5 | 「新建清洗任务」对已失败/已处理的 raw 直接报 `no raw data to clean`，且建了任务行才失败 | 提交前校验并返回 400；或提供「重新清洗此文件」重置 raw 状态 |
| 6 | 评估任务进度全程不可见（DB 只在结束时提交）：50 条要等 8 分钟，前端一直显示 0%/pending | 每 N 条 flush+commit 一次进度 |
| 7 | UI 无「触发洞察」「同步知识源」入口，洞察只能走 API | 补入口，否则洞察只能靠脚本事后触发 |
| 8 | 覆盖率对空知识库仍显示 `0%` 并提示"覆盖率偏低" | 区分「不适用（无知识库）」与「覆盖率低」 |
| 9 | 洞察对比把 LLM 随机性当业务变化：同一批数据跑两次，痛点显示"消失 3 条" | 对比前对痛点做集合归一化，或固定温度/seed |

### 产品口径问题（与知识模型重构相关）

- 这批 CSV 的 `answer` 是**人工客服原话**，评估出来的是「人工基线」，不是「AI 回复质量」；
- 用默认 5 维评 B2B 技术支持对话，**完整性 24.28** 主要反映"人工回复不会写步骤"，不宜直接当成模型能力指标；
- 知识提取把案例里的问答当知识源，正是待重构的部分（应产出 `knowledge_suggestions`，而非直接入库）。

## 四、结论

**可以作为 case，但要分清用途：**

| 用途 | 可行性 |
| --- | --- |
| 质量评估 / 报告（人工基线） | ✅ 已验证，产出可读、结论具体 |
| 洞察分析 | ✅ 可跑，但需接受 LLM 输出波动 |
| 知识提取 / 覆盖率 | ❌ 业务上不成立：案例不等于知识库 |
| 与 AI 回复对比 | ⚠️ 缺少 AI 回复列，只能当"人工基线"，不能算"AI 质量" |

**建议的正式接入方式**：从 `sessions.db`（28,581 条原始对话，26,480 条含双向发言）按公司导出
`user_message / ai_response` 两列，才是真正的「对话 case」；这 5 个 CSV 的定位是
**期望值/标签/评测集**，不是对话语料。

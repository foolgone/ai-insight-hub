## 1. 背景与定位

### 1.1 为什么自建

早期方案曾把 LangSmith 作为 Trace / Prompt 管理 / 成本统计的一站式 SaaS，并按其套餐估算月度费用。该方案已废弃，原因：

- 套餐价格与额度会变动，写进文档就会过期；
- 项目只需要「调用日志 + 指标 + 成本聚合 + 告警」，不需要 Prompt 版本管理和 A/B 实验；
- 已有 PostgreSQL / Redis / 服务器，自建边际成本接近 0；
- 数据（含用户输入）不出内网，减少合规与脱敏负担。

> 🗑️ **已过时**：旧文档中的 LangSmith Developer / Plus / Team 定价表、`$39`、`$199`、`$0.001/trace` 以及由其推导的 `$1,268`、`$1,428`、`$849` 等总额，全部作废，不再作为预算依据。

### 1.2 自建三件套

| 能力 | 组件 | 解决什么问题 | 数据落点 |
|------|------|-------------|---------|
| **日志** | Loguru | 单次调用为什么失败、耗时多久、走了哪个模型 | 文件（按天轮转）+ stdout |
| **指标** | Prometheus | 全局趋势：QPS、token 速率、成本速率、延迟分位 | Prometheus TSDB |
| **明细** | PostgreSQL `llm_calls` | 按用户 / 数据源 / 任务 / 模型聚合成本，支撑配额与降级 | 业务库 |
| **展示** | Grafana | 看板与告警面板 | 读 Prometheus + PG |

三者关系：**日志看单点，指标看趋势，明细看账**。成本对账以 `llm_calls` 为准，Prometheus 只做实时趋势与告警。

## 3. 日志：Loguru

### 3.1 初始化

# app/core/logging.py
import sys

from loguru import logger

from app.core.config import settings

# 移除默认 handler，统一由项目配置

### 3.2 LLM 调用日志字段

统一用 `logger.bind(...)` 挂结构化字段，**不要拼字符串**，否则无法按字段检索。

```python
# app/services/llm_client.py
import time

from loguru import logger


async def call_llm(llm, messages, *, task_id: str, attempt: int, agent_name: str):
    """带结构化日志的 LLM 调用"""

    log = logger.bind(
        task_id=task_id,
        attempt=attempt,
        agent_name=agent_name,
        model=getattr(llm, "model_name", "unknown"),
    )

    started = time.perf_counter()
    try:
        response = await llm.ainvoke(messages)
    except Exception as exc:
        log.bind(
            duration_ms=round((time.perf_counter() - started) * 1000, 2),
            error_type=type(exc).__name__,
        ).error("llm_call_failed: {}", exc)
        raise

    usage = getattr(response, "usage_metadata", None) or {}
    log.bind(
        duration_ms=round((time.perf_counter() - started) * 1000, 2),
        input_tokens=usage.get("input_tokens", 0),
        output_tokens=usage.get("output_tokens", 0),
    ).info("llm_call_ok")

    return response
```

建议字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `task_id` | str | 业务任务 ID，串联一次任务的全部调用 |
| `attempt` | int | 真实调用序号，从 0 开始（与 `llm_calls.attempt` 一致） |
| `agent_name` | str | 哪个 Agent 发起 |
| `model` | str | 实际使用的模型名 |
| `input_tokens` / `output_tokens` | int | 本次用量 |
| `duration_ms` | float | 端到端耗时 |
| `error_type` | str | 失败时的异常类名 |

### 3.3 脱敏规则

日志会落盘，**禁止写入原文**：

| 数据类型 | 处理方式 |
|---------|---------|
| 用户手机号 / 邮箱 | 中间打码：`138****8000`、`a***@example.com` |
| 订单号 / 会话 ID | 保留后 4 位：`****1234` |
| 完整 Prompt / 模型输出 | 只记 `prompt_chars` / `output_chars` 长度；需要排查时按 `task_id` 到 `llm_calls` 取摘要 |
| API Key / Token | 永不记录；`diagnose=False` 防止异常栈打印变量值 |

```python
# app/core/masking.py
import re

PHONE_RE = re.compile(r"(1[3-9]\d)\d{4}(\d{4})")
EMAIL_RE = re.compile(r"([\w.+-])[\w.+-]*(@[\w.-]+)")


def mask_pii(text: str) -> str:
    """对常见 PII 做脱敏，写日志前必须调用。"""
    text = PHONE_RE.sub(r"\1****\2", text)
    text = EMAIL_RE.sub(r"\1***\2", text)
    return text
```

> ⚠️ 脱敏函数只做兜底，**不要**把完整 Prompt 交给它再写日志。正确做法是根本不记录原文。

## 4. 指标：Prometheus

### 4.1 指标定义

```python
# app/core/metrics.py
from prometheus_client import Counter, Histogram

# Token 消耗（按方向、模型、Agent 维度）
llm_tokens_total = Counter(
    "llm_tokens_total",
    "Total LLM tokens consumed",
    ["model", "agent_name", "direction"],  # direction: input / output
)

# 成本（美元），由 token × 单价计算后累加
llm_cost_usd_total = Counter(
    "llm_cost_usd_total",
    "Total LLM cost in USD (token * unit price)",
    ["model", "agent_name"],
)

# 延迟（秒）
llm_latency_seconds = Histogram(
    "llm_latency_seconds",
    "LLM call latency in seconds",
    ["model", "agent_name"],
    buckets=(0.5, 1, 2, 5, 10, 20, 30, 60, 120),
)

# 调用结果
llm_calls_total = Counter(
    "llm_calls_total",
    "Total LLM calls",
    ["model", "agent_name", "status"],  # status: success / error
)
```

> 指标基数控制：`agent_name` 是有限枚举（cleaning / evaluate / extract / report 等），不要把 `task_id`、`user_id` 放进 label，否则会打爆 Prometheus。

### 4.2 埋点

```python
# app/services/llm_metrics.py
from app.core.metrics import (
    llm_calls_total,
    llm_cost_usd_total,
    llm_latency_seconds,
    llm_tokens_total,
)


def observe_llm_call(
    *,
    model: str,
    agent_name: str,
    input_tokens: int,
    output_tokens: int,
    cost_usd: float,
    duration_seconds: float,
    status: str,
) -> None:
    """在每次 LLM 调用结束后调用一次（成功/失败都要记）。"""

    labels = {"model": model, "agent_name": agent_name}

    llm_calls_total.labels(**labels, status=status).inc()
    llm_latency_seconds.labels(**labels).observe(duration_seconds)

    if input_tokens:
        llm_tokens_total.labels(**labels, direction="input").inc(input_tokens)
    if output_tokens:
        llm_tokens_total.labels(**labels, direction="output").inc(output_tokens)

    if cost_usd:
        llm_cost_usd_total.labels(**labels).inc(cost_usd)
```

## 5. 调用记录：`llm_calls`

### 5.1 与成本文档的关系

`llm_calls` 表结构、写入代码、成本公式见 `03-成本管理.md` §3.1–§3.3。本文只补充**查询与对账**用法，不重复定义表。

关键约束（与 `07-Agent错误重试机制.md` §3.5 一致）：

- `idempotency_key = f"{task_id}:{attempt}"`，唯一索引 `uk_llm_calls_idempotency`；
- 重复上报用 `ON CONFLICT ... DO UPDATE`，不新增行、不重复计费；
- `status` 取 `success` / `failed`，失败行保留 `error_type` / `error_message`。

### 5.2 常用查询

```sql
-- 今日按用户汇总（配额判定用）
SELECT user_id,
       SUM(input_tokens)  AS input_tokens,
       SUM(output_tokens) AS output_tokens,
       SUM(total_cost)    AS total_cost
FROM llm_calls
WHERE created_at >= CURRENT_DATE
GROUP BY user_id;

-- 近 7 天按模型汇总（单价调整后的效果对比）
SELECT model,
       COUNT(*)            AS calls,
       SUM(total_tokens)   AS tokens,
       SUM(total_cost)     AS cost
FROM llm_calls
WHERE created_at >= NOW() - INTERVAL '7 days'
GROUP BY model
ORDER BY cost DESC;

-- 失败率（按 Agent）
SELECT agent_name,
       COUNT(*) FILTER (WHERE status = 'failed')::float / COUNT(*) AS failure_rate
FROM llm_calls
WHERE created_at >= NOW() - INTERVAL '1 day'
GROUP BY agent_name;
```

> ⚠️ 成本对账**只用 `llm_calls`**。Prometheus 的 `llm_cost_usd_total` 是进程内累加，重启会归零（除非配置 remote write / 持久化），不能用于月度结算。

## 6. 告警与降级联动

### 6.1 阈值（引用 `03-成本管理.md` §5.1）

| 级别 | 用量比例 | 动作 | 实现位置 |
|------|---------|------|---------|
| `warning` | ≥ 0.80 | 通知，服务正常 | `CostAlertManager` |
| `throttled` | ≥ 0.90 | QPS 60 → 30 | `DegradationMiddleware` |
| `degraded` | ≥ 1.00 | 切 `DEGRADED_LLM_MODEL`，QPS → 10 | `DegradationManager` |
| `stopped` | ≥ 1.20 | 停止 AI 调用，返回 429 | `DegradationMiddleware` |

> 阈值**只在** `03-成本管理.md` §5.1 定义一次；本文与 `06-成本超限降级策略.md` 均直接引用，不得另写数字。

### 6.2 告警规则

```yaml
# deploy/prometheus/rules/llm-cost.yml
groups:
  - name: llm-cost
    rules:
      # 成本速率：按当前单价换算后的小时成本，阈值需按实际预算填写
      - alert: LLMCostRateHigh
        expr: sum(rate(llm_cost_usd_total[1h])) * 3600 > 0
        for: 30m
        labels:
          severity: warning
        annotations:
          summary: "LLM 小时成本超过预算阈值"
          description: "请核对 03-成本管理.md §0 的 P_IN / P_OUT 与月度预算。"

      # 失败率
      - alert: LLMCallFailureRateHigh
        expr: |
          sum(rate(llm_calls_total{status="error"}[10m]))
          /
          sum(rate(llm_calls_total[10m])) > 0.1
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "LLM 调用失败率 > 10%"

      # P95 延迟
      - alert: LLMLatencyP95High
        expr: histogram_quantile(0.95, sum(rate(llm_latency_seconds_bucket[10m])) by (le)) > 30
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "LLM P95 延迟 > 30s"

      # 配额接近上限（业务指标，由导出器从 llm_calls 计算）
      - alert: UserQuotaNearLimit
        expr: aiinsight_user_cost_usage_ratio > 0.8
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "用户 {{ $labels.user_id }} 成本用量超过 80%"
```

> `LLMCostRateHigh` 的 `> 0` 只是占位：预算阈值属于**待确认参数**，需在单价与月预算冻结后替换为具体数值，避免文档里出现无来源金额。

### 6.3 与降级策略的联动

```
llm_calls 聚合（今日成本）
        │
        ▼
CostAlertManager.check_and_alert()  ──► 0.80 通知
        │
        ▼
DegradationManager.get_degradation_level()
        │
        ├─ 0.90 → DegradationMiddleware 限流（QPS 30）
        ├─ 1.00 → Agent 切 DEGRADED_LLM_MODEL + 结构化输出兜底
        └─ 1.20 → 中间件直接返回 429
```

降级期间的可观测要求：

- 日志必须带 `level`（`throttled` / `degraded` / `stopped`），便于统计降级时长；
- `llm_calls.model` 会记录降级模型名，可按模型对比降级前后的失败率；
- 降级触发的结构化输出失败（`status='failed'`）需单独看板展示，避免「降级后静默失败」。

## 8. 数据保留、容量与隐私

### 8.1 保留期

| 数据 | 保留期 | 说明 |
|------|--------|------|
| 应用日志 | 30 天（错误日志 90 天） | 轮转 + gzip |
| Prometheus 指标 | 15 天（本地） | 需要更长周期时配 remote write |
| `llm_calls` | 永久（按月分区，Phase 2） | 对账依据，不删除 |

### 8.2 容量估算

`llm_calls` 单行约 200–300 字节（含索引）。按 10 万条/月估算，年增约 1.2M 行、300 MB 量级，普通 PostgreSQL 实例可承载；达到 **1000 万行** 时再按 `11-数据库分区策略调整.md` 的演进路径处理。

### 8.3 隐私

- 日志只记长度与 ID，不记 Prompt 原文；
- `llm_calls` 不存 Prompt 内容，只存 token 数与成本；
- Grafana 看板不展示用户手机号/邮箱，用户维度用 `user_id` 或脱敏名；
- 导出报表前需再过一次 `mask_pii`。

## 10. 错误追踪：Sentry（T7）

**目标**：5xx / 未捕获异常 / 前端白屏能被主动感知，而不是等用户反馈。

| 端 | 实现 | 触发点 |
| --- | --- | --- |
| 后端 | `app/core/sentry.py`：`init_sentry()` 启动时初始化；`capture_exception()` 统一上报 | 全局异常 handler：未捕获异常、领域异常中 `status >= 500`（4xx 不上报，避免噪声） |
| 前端 | `src/lib/sentry.js`：动态 import `@sentry/react`，`VITE_SENTRY_DSN` 为空时 no-op | `main.jsx` 启动初始化；`ErrorBoundary.componentDidCatch` 上送组件栈 |

配置（`.env`）：

```bash
SENTRY_DSN=                 # 留空 = 关闭
SENTRY_ENVIRONMENT=production
SENTRY_TRACES_SAMPLE_RATE=0.0   # 0 = 只报错不采样性能
SENTRY_SEND_DEFAULT_PII=false
VITE_SENTRY_DSN=            # 前端同理
VITE_SENTRY_TRACES_SAMPLE_RATE=0
```

约束：

- 上报失败绝不影响业务（内部 try/except + 日志告警）；
- 测试/本地不配 DSN 即完全静默，不产生外网请求；
- PII 默认关闭（`send_default_pii=false`），Prompt 原文不进 Sentry。

# 21 · 批次对比与效果验证

> 状态：已落地（后端 2026-11-11，迁移 016）
> 动机：产品只会说「我们发现 14 个问题」，客户真正要的是「改完之后有没有变好」。

---

## 1. 问题

评估结果都写 `analysis_results`，但**没有任何字段记录它由哪个任务产生**。后果：

- `GET .../analysis/quality` 只能按数据源全量查（`datasource_id + analysis_type`），
  想比较「本次 vs 上次」只能按 `created_at` 猜；
- 平均分是数据源级的累计值，改动前后的对比无法成立；
- 报告只能描述现状，无法证明「改了知识库/话术之后质量提升了」。

这是「分析工具」和「可续费的运营系统」之间的分界线。

## 2. 方案

**一次任务 = 一个批次（run）。** 最小改动是把批次归属补上，而不是新建一套 run 表：

| 改动 | 内容 |
| --- | --- |
| 迁移 016 | `analysis_results` 增加 `task_id`（nullable）+ `idx_analysis_task_id`；**不回填历史数据** |
| 写入 | 评估 / 洞察 / 转录摘要三处写入点补 `task_id` |
| 读取 | 新增 `GET .../runs`（批次列表）与 `GET .../runs/{a}/compare/{b}`（对比） |
| 前端 | 质量评估页新增「批次对比」面板：默认「最新 vs 上一次」，可手选 |

设计取舍：

1. **不建 run 表**：`tasks` 已经是运行记录（状态、结果、耗时、成本都在），再建一层只会双写；
2. **历史数据不回填**：按时间就近匹配会伪造归属，宁可让老批次不可比（接口返回 409 并说明）；
3. **对比维度三层**：总分/维度（趋势）→ 分数档位（结构）→ 单条对话（可定位）；
   只给平均分是最容易被误读的做法（一涨一跌会互相抵消）；
4. **问题文本只做差集**：issues 是 LLM 自由文本，没有稳定 ID，所以归一化后求差集，
   在响应和 UI 里都标注「线索而非精确指标」，不假装是精确指标；
5. **样本差异单独暴露**：`added_items` / `removed_items` 防止把「这次少评了 20 条」误读成「质量提升」。

## 3. 关键实现

| 位置 | 说明 |
| --- | --- |
| `migrations/versions/..._016_analysis_results_task_id.py` | 加列 + 索引，无外键（任务可能被清理，与 `llm_calls.task_id` 一致） |
| `app/services/run_service.py` | `list_runs` / `compare_runs` + 纯函数 `build_comparison`（可单测） |
| `app/repositories/analysis_results.py` | `list_for_task` / `aggregate_by_task` |
| `app/api/v1/analysis.py` | 两个只读端点，沿用现有 RBAC |
| `frontend/src/components/quality/RunComparisonPanel.jsx` | 批次选择 + 概览/维度/对话/问题四段对比 |

对比口径：

- 分数按对话 `data_id` 对齐，只列分差 ≥ 1 分的 Top 5（避免浮点噪声刷屏）；
- 分数档位阈值与前后端一致：≥90 优秀 / ≥75 良好 / ≥60 合格 / <60 较差；
- 平均分保留 2 位小数。

## 5. 已知边界与后续

- **历史批次不可比**：016 之前的结果没有 `task_id`，需要重跑一次评估才能进入对比；
- **只看评估**：洞察/摘要虽然也带 `task_id`，但暂未提供对比视图（洞察是数据源级单条结果，
  对比价值低于逐条评分，等有需求再做）；
- **问题分类仍是自由文本**：下一步可让评估 Agent 输出 `issue_category`
  （幻觉 / 知识缺失 / 话术 / 合规 / 流程），才能做「TOP 5 问题 + 改进台账」；
- **没有「改进项 → 复测」闭环**：本轮只解决「能不能比」，不解决「谁来改、改完通知谁」。

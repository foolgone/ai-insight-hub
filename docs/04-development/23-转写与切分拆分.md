# 23 · 转写与切分拆成两步

> 状态：已落地（2026-11-12，迁移 017）
> 前置：`22-长转写分块与结构化修复.md`（分块 + 修复轮 + 失败可见）

---

## 1. 为什么要拆

原来是「一个 clean 任务 = 转写 + 切分 + 落库」：

- 切分失败或效果不好，**只能重跑整条清洗**，转写结果虽然复用，但语义上混在一起；
- 用户看不到「这个文件转写好了没 / 切分了没」；
- 重试按位置合并（`uuid5(raw_id:qa-{序号})`），条数变化时会新旧混排。

拆成两步后：**转写只做转写，切分可独立重试，且每次整体替换对话结果**。

## 2. 数据流

```
上传 ──clean 任务──> ① 转写：text/segments 写入 raw_content
                         │（单声道整段）
                         └─建 structure 任务 → 自动入队──> ② 切分：分块 → QA/知识点/摘要
                                                              ├─ 成功：删除该文件旧对话 → 写入新结果
                                                              └─ 失败：structure_error + 任务 failed（可单独重试）
```

双声道（L/R 已配对）不进入切分：clean 任务直接产出对话行，行为不变。

## 4. 行为约定

1. **默认自动串联**：转写完成后 clean 任务返回 `structure_task_ids`，Celery 适配层入队切分——用户上传仍然是一步；
2. **切分可单独重试**：`POST .../raw-data/{raw_id}/structure`；同一文件同时只允许一个切分任务（409）；
3. **整体替换**：切分成功后先删该 `raw_data_id` 派生的所有对话，再写入新结果（同一 raw 重跑不会产生重复/混排）；
4. **前置校验**：非媒体 → 409「只有音视频需要切分」；未转写 → 409「尚未完成转写」；双声道 → 409「已配对，无需切分」；
5. **失败语义**：切分失败时任务 failed 且 `structure_error` 有原因，原始文本仍在 `raw_content.text`，不影响转写结果与重试。

## 6. 已知边界

- 切分产生的**知识点 / 摘要**没有按文件「整体替换」的归属键（`knowledge_base` 无 `raw_data_id`），
  同一文件多次切分为 knowledge 时可能追加重复条目；QA 路径无此问题。
- 仍无「手动指定问答边界」入口。
- 历史单声道文件（拆分前产生）会有 1 条整段记录；点「重新切分」时会先删掉它再写新问答（替换语义）。

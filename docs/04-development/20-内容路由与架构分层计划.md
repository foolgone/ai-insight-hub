# 20 · 内容路由与架构分层计划

> 状态：已落地（P1–P4 完成）
> 关联：`19-音视频ASR转写MVP设计.md`、`03-architecture/03-数据库设计.md`
> 触发背景：面试录音（单声道）转写完成后，系统只能落一条整段文本，既无法切成问答对，也没有承载「知识点 / 摘要」的数据形态。

---

## 1. 两个问题

### P1 · 内容路由缺失

系统目前是**固定管线**：

```text
文本上传  → 清洗 Agent → 对话 JSON → 评估 / 知识提取 / 洞察
ASR 转写  →（跳过 Agent）→ 直接落库
```

- 「文本 → 对话 JSON」的能力**存在**（`cleaning_agent`），但只用于文本上传；
- 媒体分支（`cleaning_service` 的 `if is_media:`）刻意跳过清洗 Agent，只做「取 ASR records → 去重 → 落库」；
- 没有任何环节判断「这段内容应该做成 QA、知识点还是摘要」。

结果：一条 35.8 分钟的面试录音，最终只是 `cleaned_data` 里一条 7615 字的 `user_message`，`ai_response` 为空、`quality_score` 为 `NULL`，无法评估、无法沉淀知识。

### P2 · 分层与解耦不足

当前目录按**文件类型**划分（`api` / `services` / `agents` / `models`），而不是按**职责**划分。具体证据：

#### 2.1 任务编排没有独立层，服务之间双向依赖

```text

cleaning_service    →（函数内延迟导入）task_service

insight_service     →（函数内延迟导入）task_service
knowledge_service   →（函数内延迟导入）task_service
```

## 3. 目标与非目标

### 目标

1. 增加「内容路由」：转写文本 → AI 判断 → QA / 知识点 / 摘要，并落到对应存储。
2. 建立清晰边界：`api → application → domain ← infrastructure`，服务之间不再互相 import。
3. 每个阶段独立可上线、可回滚。

### 非目标

- 不做大爆炸重构，不引入 DDD 全套（聚合根、领域事件总线等）。
- 不改变现有对外 API 契约（除新增能力）。
- 不重写前端设计体系。

---

## 4. 目标架构（渐进式）

```text
app/
  api/            HTTP：鉴权、参数校验、状态码、DTO 映射（不含业务规则）
    ↓
  application/    用例编排：upload / clean / evaluate / structure
    ↓
  domain/         实体与规则：TaskState、ContentType、Structure、MediaAsset
    ↑
  infrastructure/ 端口实现：storage、llm、asr provider、repositories
    ↑
  agents/         LLM 能力（被 application 调用，不反向依赖）
```

### 三条硬规则

1. `api` 只依赖 `application`，不得直接 import `services` / `agents`；
2. `application` 之间不互相 import，跨用例协作通过 `domain` 服务或事件；
3. 禁止函数内 `from app.services import ...`（当前 12 处），以此消除循环依赖。

### 迁移方式

绞杀者（Strangler）：新能力按新分层编写；旧代码仅在**被本次改动触及时**搬迁；每个 PR 都必须保持现有测试全绿。

## 5. 内容路由设计

### 5.1 数据流

```text
转写文本 + 元信息（时长 / 声道模式 / 来源）
  ↓ 结构化 Agent（1 次 LLM 调用）
{
  content_type: interview | customer_service | meeting | monologue | other,
  structure:    qa | knowledge | summary,
  confidence:   0-1,
  qa:        [{ question, answer, quality_score, issues }],
  knowledge: [{ title, content, tags }],
  summary:   "...",
  rationale: "模型自述的判断依据"
}
  ↓ 落 raw_content.structured（JSONB，含 schema_version）
  ↓ 按 structure 分流
qa        → cleaned_data（question→user_message，answer→ai_response）
knowledge → knowledge_base（二期，status=pending 待审核）
summary   → analysis_results（二期，analysis_type=insight）
```

### 5.2 关键决策

| 决策点 | 方案 | 理由 |
| --- | --- | --- |
| 角色映射 | **AI 判断**谁是提问方、谁是回答方；系统只做字段映射（question→`user_message`，answer→`ai_response`） | 面试、客服、会议的角色不同，写死会错 |
| 触发条件 | 仅 `speaker_pair=mono` 且文本长度 ≥ 阈值（默认 200 字） | 短音频结构化收益低，避免浪费调用 |
| 失败降级 | LLM 失败 / schema 校验失败 → 保留单条整段文本，标记 `structure_unparsed` | 不阻断清洗，数据不丢 |
| 质量分 | 由模型给 0–100（评回答的完整性 / 相关性 / 表达），判断不了给 `null` | 结构化后即可进入评估链路 |
| 时间戳 | 单声道无时间戳，统一 `null` | 不编造 |
| 可观测 | 结构化结果写 `raw_content.structured`；任务 result 增加 `structure` 摘要（类型 / 条数 / 置信度） | 便于排查与统计 |

### 5.3 与现有链路的关系

- 结构化发生在**媒体分支的转写之后、落库之前**；
- 产出 `qa` 时，用结构化结果替换原来的「单条整段文本」记录；
- 产出 `knowledge` / `summary` 时，保留单条记录（不丢原文），结构化结果另存 `structured`，待 P5 分流。

## 12. 分层纪律（P1 后续 · import-linter）

计划里的「P1 引入 import-linter」已落地，先固化四条**不许回退**的硬边界，
等 P2（端口 Protocol）/ P3（repository）完成后再升级为 `layers` 契约。

| 契约 | 含义 |
| --- | --- |
| `http-layer-not-depended-on` | `services / application / agents / tasks / models / schemas` 不得 import `api` |
| `core-is-leaf` | `app.core` 不得依赖业务层（只能被依赖） |
| `data-layer-is-leaf` | `models / schemas` 不得依赖上层 |
| `api-not-import-tasks` | API 不得直接 import Celery 任务（只约束直接 import，service 入队允许） |

配套修复的分层倒置：`services` 原先从 `app.api` 导入 `assert_owner` 与分页工具，
现移到 `app/core/ownership.py` 与 `app/core/pagination.py`（12 个文件改导入，`app/api/pagination.py` 删除）。

## 13. 端口（Port）抽象（P2）

业务代码依赖 Protocol，而不是具体实现。当前三个端口：

| 端口 | 现有实现 | 说明 |
| --- | --- | --- |
| `LLMPort` | `app.core.llm.LLMClient` | `chat()` / `aclose()`；`BaseAgent` 已按端口注入，测试可传 fake |
| `StoragePort` | `app.services.storage_service`（模块级函数） | 模块对象直接满足协议，无需包类 |
| `TranscriberPort` | `app.services.media_service` | 返回写回 `raw_content` 的字段字典 |

配套调整：

- `AsrConfig` / `detect_protocol` / 协议常量从 `asr_service` 移到 `app.ports.asr`（纯数据与纯逻辑），
  `asr_service` 保留同名再导出，老 import 不受影响；
- 新增契约 `ports-are-inner`：`app.ports` 不得依赖 `api / services / application / agents / tasks`；
- `tests/unit/test_ports.py`：用 `runtime_checkable` 断言具体实现满足协议，签名漂移会立刻失败。

还没做的：`media_pipeline` 仍直接调用 `media_service.transcribe_media`（未通过构造参数注入），
`extraction_agent` 仍直接 import `embedding_service`；这两处在 P3 抽 repository 时一并收口。

## 14. 仓储层（P3）

把 SQL 从 service 收敛到 `app/repositories/`，service 只表达「要什么」。

| 仓储 | 覆盖 | 方法 |
| --- | --- | --- |
| `cleaned_data` | 5 个 service / 25 处查询 | `list_for_datasource` / `get` / `list_for_analysis` / `load_evaluable` / `count_for_datasource` / `insert_ignore_conflicts` |
| `knowledge_base` | 4 个模块 / 31 处查询 | `list_for_datasource` / `get` / `existing_questions` / `nearest_questions` / `delete_seed` / `search` / `count_by_status` / `count_by_source` |

设计取舍：

- **只搬 SQL，不搬规则**：去重策略仍在 `knowledge_dedup`，冷启动状态机仍在 `knowledge_status`，
  归属校验仍在 service（`assert_owner`）。仓储只管「怎么查」，不管「能不能查」。
- **排序白名单随查询一起下沉**：`SORTABLE` 从 service 移到仓储，避免两处维护。
- **契约兜底**：`repositories-are-inner` 保证仓储不反向依赖 `services / application / agents / api`。

现状契约（`lint-imports`，6 kept）：

```
http-layer-not-depended-on   services/application/agents/tasks/models/schemas 不得 import api
core-is-leaf                 app.core 不得依赖业务层
data-layer-is-leaf           models/schemas 不得依赖上层
api-not-import-tasks         API 不得直接 import Celery 任务
ports-are-inner              app.ports 不得依赖实现层
repositories-are-inner       app.repositories 不得依赖上层
```

> 距离单向 `layers` 契约还差一步：`services → application`（5 处）与 `application → services`（1 处）
> 仍双向。下一步要么把 `media_pipeline` 的 asr/media 依赖改成注入，要么把
> `task_control` 归到更底层，二者选一即可让 `application` 成为纯上层。

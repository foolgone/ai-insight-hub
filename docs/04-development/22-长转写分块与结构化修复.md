# 22 · 长转写分块与结构化修复

> 状态：已修复（2026-11-11，后端 + 前端）
> 触发问题：上传 39 分钟面试录音（`众联成业面试录音.mp3`，56.7MB，转写 9318 字）后，
> 结果落成**一整段 9318 字、`ai_response` 为空**的单条记录，没有切出任何问答。

---

## 1. 现象与根因

### 1.1 事实（来自云端真实数据）

| 项 | 值 |
| --- | --- |
| 转写 | `qwen3-asr-flash`，10 个切片，2364.7s，文本 9318 字，`asr_status=completed` ✅ |
| 记录形态 | `records=1`，`speaker_pair=mono`（单声道整段，本应进入结构化） |
| 结构化 | **失败**：`llm_calls` → `structure_agent / failed / AgentOutputError / structure=summary but summary is empty / 0 tokens / 28.3s` |
| 落库 | `raw_content.structured` 不存在；`tasks.result` 只有 `asr`，没有 `structure` |
| 对比 | 同功能另一次成功调用（11-09）`structure=qa`、14 组问答，**输出 6499 token**（首轮 + 修复轮） |

### 1.2 三层叠加的原因

1. **长文本必然打满输出上限**：`DEFAULT_MAX_TOKENS=4096`（云端实测），结构化沿用全局值；
   39 分钟面试的问答对远超 4096 token，首轮 JSON 被截断 → 解析失败。
2. **修复轮只保证 JSON 合法**：`parse_with_repair` 收到截断文本后，最小合法解就是
   `{"structure":"summary","summary":""}`——schema 通过，内容为空。
3. **业务校验不在修复回路**：`structure_agent._validate_output` 抛 `AgentOutputError`
   （`retryable=False`），且发生在 `async_retry` 之外 → 不再重试；
   `structure_service.apply` 按「失败不阻断清洗」降级 → 保留整段文本。

并伴随两个观测缺口：降级**没有任何标记**（界面看起来像正常结果）、失败调用**漏记 token**（0/0）。

## 2. 修复方案

| # | 改动 | 文件 |
| --- | --- | --- |
| 1 | **分块结构化**：按句末标点切块（≤2500 字/块，最多 12 块，超限只合并尾巴不丢内容），逐块调用后合并 | `application/structure_service.py` |
| 2 | **合并规则**：QA 按「问题+答案」归一化去重（保留更高分）、`content_type` 多数票、confidence 取均值、summary 拼接截断 | 同上 |
| 3 | **输出上限单列**：结构化 Agent `max_tokens=8192`、`timeout=120s`（不再共用全局 4096/60s） | `agents/structure_agent.py` |
| 4 | **业务校验进入修复轮**：`parse_with_repair(validator=...)` + `BaseAgent._validate_parsed` 钩子；修复提示词明确「空字段必须用原文补全，否则改选形态」 | `agents/structured_output.py`、`agents/base.py` |
| 5 | **失败可见**：全失败写 `raw_content.structure_error` + 记录打 `structure_unparsed` + `task.result.structure_error`；部分失败标 `partial`/`failed_chunks`/`structure_partial` | `structure_service.py`、`services/cleaning_service.py` |
| 6 | **失败也记账**：`record_failure(usage=...)`，首轮 + 修复轮 token 一并回填 | `core/cost_tracker.py`、`agents/base.py` |
| 7 | **提示词收紧**：面试/客服「能分辨问答就必须用 qa」；`summary` 不得为空（`v1.1.0`） | `prompts/structure/system.txt` |
| 8 | **前端提示**：清洗详情页把 issue 码翻成中文，并对「未切分 / 部分切分」显示提示条（说明可重试、转写会复用） | `frontend/src/lib/issues.js`、`components/cleaning/CleanedDataDrawer.jsx` |

### 2.1 关键参数

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `CHUNK_MAX_CHARS` | 2500 | 每块输出约 300–800 token，远离 8192 上限 |
| `MAX_CHUNKS` | 12 | 约 3 万字上限；超出只合并尾巴，不丢内容 |
| `STRUCTURE_MAX_TOKENS` | 8192 | 单块输出的安全余量（实测 6.5k 也能容纳） |
| `STRUCTURE_TIMEOUT` | 120s | 输出变长，60s 容易超时 |

### 2.2 设计取舍

- **按句切、不按字数硬切**：避免把「提问」和「回答」切到两个块里；单句超长（ASR 无标点）才硬切。
- **块级失败隔离**：某一块失败时保留其它块的结果（`partial=True`），而不是整体降级。
- **修复轮而不是直接失败**：业务规则（形态与内容自洽）与 JSON 合法性一样，都值得一次带明确指令的重试。
- **不重复计费**：分块后每块的成本幂等键是 `structure:{task_id}:{chunk_index}`，不再互相覆盖。

## 4. 影响与回滚

- **行为变化**：长录音的结构化调用次数从 1 次变为 N 次（N≈文本长度/2500，最多 12），
  但每次输出更短、更稳定；总 token 不升反降（少了「截断 + 修复 + 失败重跑」）。
- **失败语义**：以前静默降级，现在会明确标记并给出原因；`task.result` 新增 `structure_error`。
- **回滚**：本次无迁移；回滚代码即回到整段降级行为（数据不受影响）。

## 5. 后续（未做）

- 结构化仍受 `MEDIA_STRUCTURE_MIN_CHARS=200` 门槛限制，极短录音不切分（预期行为）；
- 分块之间没有 overlap，跨块的追问可能被拆到两组；如需更严格可加 200 字重叠并去重；
- 「重试拆分」目前复用清洗任务重试（会跳过已完成的 ASR），没有独立的「只重跑结构化」入口。

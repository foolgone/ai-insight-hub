## 1. 背景

### 1.1 当前状态

项目功能闭环已经完整：上传 → 清洗 → 评估 → 知识提取 → 洞察 → 报告，BYOK、降级、SSE、PDF 报告均已落地，测试与 CI 门禁齐全。

但存在两类结构性问题：

1. **数据不可信**：几处一致性缺陷导致「成本统计」「报告洞察」「任务重试」在特定场景下产出错误结果，而这些数据正是对外展示的核心指标。
2. **质量不可验证**：AI 输出的好坏没有基准。`tests/prompt/golden_outputs/` 只有 README，Prompt 测试只做结构断言（字段齐、分数在 0–100），无法回答「这次改动让效果变好了吗」。

### 1.2 借鉴来源

`weknora-eval` 是一套离线评测框架，其工程模式值得借鉴（实现本身是单租户 CLI + 文件系统，不可直接移植）：

| 模式 | 核心做法 |
|---|---|
| 三份数据契约 | `EvalSample` / `RunResult` / `JudgeResult` 层间解耦，带 `schema_version` |
| 清洗分层 | 「剥除类」直接删、「判定类」只标记不删 |
| 可复现评测集 | 真实会话挖 gold + 分层抽样 + 固定 seed + `latest/archive` 版本化 |
| 离散裁判 | 0–3 分档位 + `temperature=0` + 「未测出 ≠ 0 分」 |
| 可追溯报告 | 均值 + 分位数 + 离散分布 + 分组 + 低分回流 + 未对齐显式列出 |

### 1.3 目标（可验收）

| 目标 | 验收口径 |
|---|---|
| **数字可信** | 成本表行数 = 实际 LLM 调用次数；报告洞察覆盖率 100% |
| **任务可控** | 重试后任务真正执行；取消后 worker 在 1 个条目内停止 |
| **质量可验证** | 有 50+ 条人工基准；改 Prompt/模型能跑出可对比的分数 |
| **能力可见** | 5 类长任务统一进度；洞察与成本有前端入口 |

## 3. 总体方案

```
阶段一（P0+P1）一致性修复        ← 数字先可信
   ↓ 依赖：无
阶段二（P2-1~3）质量基建          ← 效果可验证
   ↓ 依赖：阶段一的成本/任务数据正确
阶段三（P2-4~6）三端体验          ← 能力可见
   ↓ 依赖：阶段二的评测数据结构
```

**三条主线**

1. **可信链路**：任务 → 产物 → 指标，每一环都能回溯到输入与版本。
2. **质量闭环**：低分样本 → 评测集 → 回归 → 对比。
3. **三端贯通**：后端写数据 → 前端展示 → 用户决策。

## 4. 解决方式

### 阶段一：一致性修复

#### 4.1 洞察结果落库（P0-1）

**方案**：`insight_service` 在 Agent 成功后，除写 `task.result` 外，同步写一行 `analysis_results`（`analysis_type='insight'`），保持「报告只认 `analysis_results`」的单一数据源。

**数据模型变更**（迁移 `012_consistency_fixes`，本阶段共用）：

```sql
-- ① 洞察是「数据源级」结果，没有单条对话；data_id 当前 NOT NULL
ALTER TABLE analysis_results ALTER COLUMN data_id DROP NOT NULL;

-- 报告查询是 (datasource_id, analysis_type) 组合 + created_at 倒序
CREATE INDEX idx_analysis_ds_type_created
    ON analysis_results (datasource_id, analysis_type, created_at DESC);

-- ② 时间戳缺失时不再伪造「当前时间」，改为存 NULL（见 4.6 P1-6）
ALTER TABLE cleaned_data ALTER COLUMN timestamp DROP NOT NULL;

-- ③ 清洗写入幂等（见 4.6 P1-5）：先去重（保留每个键最新一条）再加唯一约束
DELETE FROM cleaned_data a USING cleaned_data b
 WHERE a.raw_data_id = b.raw_data_id
   AND a.dialogue_id = b.dialogue_id
   AND a.ctid < b.ctid;   -- 删物理靠前（更早插入）的重复行 → 保留最新
CREATE UNIQUE INDEX uk_cleaned_raw_dialogue
    ON cleaned_data (raw_data_id, dialogue_id);
```

**代码改动**

| 文件 | 改动 |
|---|---|
| `backend/migrations/versions/20261105_*_012_consistency_fixes.py` | 新增：`analysis_results.data_id` 可空 + 复合索引；`cleaned_data.timestamp` 可空；`(raw_data_id, dialogue_id)` 唯一索引（含历史去重） |
| `backend/app/models/analysis.py` | `data_id` 改为 `Mapped[uuid.UUID \| None]` |
| `backend/app/models/datasource.py` | `CleanedData.timestamp` 改为 `Mapped[datetime \| None]` |
| `backend/app/services/insight_service.py` | 成功后按 `evaluation_service` 的既有模式落库（字段以 `AgentResult` 实际所有为准，**没有 confidence**）：<br>`AnalysisResult(datasource_id=task.datasource_id, data_id=None, analysis_type="insight", result=payload, agent_name=str(result.metadata.get("agent", "insight_agent")), agent_version=str(result.metadata.get("version", "v1.0.0")), ai_model=str(result.metadata.get("model", "")) or None, processing_duration=result.duration, token_usage=result.token_usage, cost=float(result.cost))`<br>（注意 `result.cost` 是 `Decimal`，需 `float()` 转换，与 `evaluation_service` 现行写法一致） |
| `backend/app/schemas/analysis.py`（如有） | 响应模型允许 `data_id` 为空 |

**要点**

- 洞察多次执行保留历史，报告取最新（现有 `order_by(created_at.desc())` 已满足）。
- 与 `quality` 结果的差异要在文档中写明：`quality` 是逐条、`insight` 是数据源级。
- 不做「回填历史数据」：历史 `tasks.result` 中的洞察不迁移（避免一次性脚本风险）。

**验证**

```sql
-- 跑一次洞察后
SELECT analysis_type, data_id, created_at FROM analysis_results
WHERE datasource_id = '<id>' AND analysis_type = 'insight';
```

```bash
# 生成 comprehensive 报告后，检查 data.insight 非空、metadata 无 insight_degraded
curl -s .../reports/{id} | jq '.data.insight, .data.metadata'
```

**回滚**：`alembic downgrade -1`（索引与可空属性可逆）；代码回退即可，已写入的 insight 行不影响旧逻辑（旧逻辑不读它们）。

#### 4.2 成本幂等键修复（P0-2）

**方案**：幂等键从 `{task_id}:{attempt}` 改为 `{task_id}:{scope}:{attempt}`，`scope` 由调用方给出，标识「同一任务内的第几次业务调用」。

**键设计**

| 场景 | scope 取值 | 示例 |
|---|---|---|
| 清洗 | `clean:{raw_data_id}` | `8f2c...:clean:1a3b...:0` |
| 评估 | `eval:{cleaned_data_id}` | `8f2c...:eval:9d1e...:0` |
| 提取 | `extract`（每任务一次） | `8f2c...:extract:0` |
| 洞察 | `insight` | `8f2c...:insight:0` |
| 报告 | `report:{report_id}` | `8f2c...:report:7c1a...:0` |
| 无 task 的临时调用（如 BYOK verify） | `adhoc:{业务键}` | `adhoc:verify:{user_id}:0` |

> 报告的 `task_id` 依赖 4.5 先落地（当前报告无 `tasks` 记录、走 `adhoc`）。**实施顺序：4.5 → 4.2**；4.5 未落地前的过渡形态为 `adhoc:report:{report_id}:{attempt}`，两形态不冲突（键不同）。

长度校验：UUID(36) + 冒号 + 前缀(≤10) + UUID(36) + 冒号 + 数字 ≈ 90 字符，`idempotency_key` 为 `String(200)`，安全。

**代码改动**

| 文件 | 改动 |
|---|---|
| `backend/app/core/cost_tracker.py` | `idempotency_key(task_id, attempt, *, scope="")`；`track()` / `record_failure()` 增加 `scope` 参数 |
| `backend/app/agents/base.py` | `invoke()` 增加 `scope: str \| None = None`，透传给 `_track_success/_track_failure` |
| `backend/app/services/cleaning_service.py` | 调用 `agent.clean(..., scope=f"clean:{raw.id}")` |
| `backend/app/services/evaluation_service.py` | `scope=f"eval:{item.id}"` |
| `backend/app/services/knowledge_service.py` / `insight_service.py` | `scope="extract"` / `"insight"` |
| `backend/app/services/report_service.py` | `scope=f"report:{report.id}"` |

**要点**

- 保持 `ON CONFLICT (idempotency_key) DO UPDATE`：同一 `scope` 的失败重试仍覆盖同一行（符合 D-03「按真实 attempt 回写」）。
- 历史数据不迁移：老键与新键不冲突，只是新旧口径并存；报表按 `created_at` 过滤即可。
- 补一条单测：同一任务 3 次不同 scope 调用 → `llm_calls` 3 行。

**验证**

```sql
SELECT count(*) FROM llm_calls WHERE task_id = '<id>';
-- 清洗 3 个文件应 = 3（修复前 = 1）
```

**预测**：demo 场景（3 raw + 100 条评估）成本行数从 1 → 103，成本金额统计误差从 −99% 收敛到 0。

#### 4.3 重试真正入队（P0-3）

**方案**：`task_service.retry` 按 `task_type` 分派到**已有的** `enqueue_*` 函数，并回写 `celery_task_id`。

**现状澄清**（v1.1 修正）：5 个 service 的入队函数**全部已存在**，无需新增——

```
cleaning_service.enqueue_clean:133(task)      evaluation_service.enqueue_evaluation:54(task)
insight_service.enqueue_insight:43(task)      knowledge_service.enqueue_extract:58(task)
report_service.enqueue_report:61(report)   ← 唯一异构：接收 Report 而非 Task
```

**代码改动**

| 文件 | 改动 |
|---|---|
| `backend/app/services/task_service.py` | `retry()` 增加 `task_type → enqueue_*` 分派，回写 `celery_task_id` |
| `backend/app/services/report_service.py` | `enqueue_report` 增加 Task 形态入参（依赖 4.5 落地；或提供 `enqueue_report_by_task(task)` 按 `task.params.report_id` 取 Report 后投递） |

**要点**

- 分派失败（未知 `task_type`）→ 抛 `TaskNotRetryableError`，不要静默成功。
- 重试前清理 `task.result` / `current_step`，避免前端看到上一次的残留状态。
- `report` 类型依赖 4.5 先建 `tasks` 记录，实施顺序：**4.5 → 4.3**。

**验证**：失败任务点重试 → `celery_task_id` 变化 → worker 日志出现新任务 → 最终状态 `completed`。

#### 4.4 取消真正停止（P0-4）

**方案**：双层控制。

1. **入口层**：`cancel()` 调 `celery_app.control.revoke(celery_task_id, terminate=False)`（不 terminate，避免半写事务）。
2. **执行层**：各 `_execute_*` 在循环内每处理完一个条目检查一次数据库状态，发现 `cancelled` 立即停止并保留已处理结果。

**代码改动**

| 文件 | 改动 |
|---|---|
| `backend/app/services/task_service.py` | `cancel()` 增加 revoke 调用（`celery_task_id` 为空则跳过）；新增 `is_cancelled(session, task_id) -> bool`（轻量 `SELECT status`） |
| `backend/app/services/cleaning_service.py` | **有逐条循环**：循环内 `if await task_service.is_cancelled(session, task.id): break` |
| `backend/app/services/evaluation_service.py` | **有逐条循环**：同上 |
| `backend/app/services/insight_service.py` / `knowledge_service.py` | **单次 Agent 调用、无循环**（`insight:152`、`knowledge:322`）：循环内检查不适用，仅依赖 revoke + 入口检查，**不列入本项改动** |

**要点**

- 取消后的 `task.status` 必须保持 `cancelled`，不能在收尾时被覆盖为 `completed`（收尾逻辑加 `if task.status == "cancelled": return`）。
- 已处理的条目保留（符合「宁低分不丢弃」）。
- 检查频率：每条目一次；1000 条评估 = 1000 次轻查询，可接受；如需优化改为每 10 条一次。

**验证**：100 条评估跑到 30 条时取消 → 5 秒内停止 → 状态 `cancelled` → 已写入结果保留。

### 阶段二：质量基建

#### 4.7 评测数据模型（迁移 `013`）

```sql
CREATE TABLE eval_datasets (
    id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    name          varchar(100) NOT NULL,
    version       varchar(20)  NOT NULL,      -- v1 / v2
    sample_count  integer      NOT NULL DEFAULT 0,
    source        varchar(50)  NOT NULL,      -- demo / real / synthetic
    meta          jsonb        NOT NULL DEFAULT '{}',
    created_at    timestamp  NOT NULL DEFAULT now(),
    UNIQUE (name, version)
);

CREATE TABLE eval_samples (
    id                 uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    dataset_id         uuid NOT NULL REFERENCES eval_datasets(id) ON DELETE CASCADE,
    question           text NOT NULL,
    gold_answer        text NOT NULL,
    category           varchar(50),
    difficulty         varchar(20),
    expected_issues    text[],
    source_dialogue_id uuid,                  -- 可回链 cleaned_data
    created_at         timestamp NOT NULL DEFAULT now()
);

CREATE TABLE eval_runs (
    id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    dataset_id     uuid NOT NULL REFERENCES eval_datasets(id),
    agent_name     varchar(100) NOT NULL,
    prompt_version varchar(50),
    model          varchar(100),
    status         varchar(20) NOT NULL DEFAULT 'pending',
    summary        jsonb NOT NULL DEFAULT '{}',  -- 均值/分位/分布/分组
    started_at     timestamp,
    completed_at   timestamp,
    created_at     timestamp NOT NULL DEFAULT now()
);

CREATE TABLE eval_results (
    id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    run_id         uuid NOT NULL REFERENCES eval_runs(id) ON DELETE CASCADE,
    sample_id      uuid NOT NULL REFERENCES eval_samples(id) ON DELETE CASCADE,
    score          smallint,                  -- 0-3，NULL = 未测出
    reason         text,
    error_type     varchar(50),               -- llm_error/parse_error/empty_answer/run_error
    latency_ms     integer,
    tokens         integer,
    cost           numeric(12, 6),
    created_at     timestamp NOT NULL DEFAULT now(),
    UNIQUE (run_id, sample_id)
);
```

**要点**

- `score` 允许 `NULL`：区分「未测出」与「0 分」（借鉴 weknora 的关键口径）。
- 统计只对 `score IS NOT NULL` 计算均值/分位。
- 时间列用 **naive `timestamp`**（不用 `timestamptz`）：与现有全部模型一致（`analysis.py` 等均为 `DateTime` + 服务层 `_now_naive()`），避免混用导致比较/排序隐性 bug。
- `cost` 用 `numeric(12,6)` 而非项目惯用的 `Float`：金额累加场景 decimal 更稳（有意为之，不追随现有口径）。

#### 4.8 Golden Set 构建（50–100 条）

| 来源 | 数量 | 说明 |
|---|---|---|
| demo 种子对话 | 10–15 | 已验证、可复现，作为冒烟基线 |
| 真实客服会话（脱敏） | 35–60 | 从 `cleaned_data` 抽样，覆盖各质量档位 |
| 人工构造边界样例 | 5–10 | 空回复、答非所问、时间缺失、重复 |

**抽样规则**（借鉴 weknora）

- 分层：按 `quality_score` 分档（<60 / 60–80 / 80–100）与 `category` 分层。
- 固定 `seed`，抽样脚本可重跑得到同一批样本。
- 每条记录 `source_dialogue_id`，可回链原始对话。

**交付物**

- `backend/scripts/build_eval_set.py`（生成 JSONL + 写入 `eval_datasets/eval_samples`）
- `backend/data/eval/golden_v1.jsonl`（可入库的样本快照）

#### 4.9 0–3 离散裁判

**方案**：新增 `backend/app/services/judge_service.py`，与业务 Agent 分离。

| 项 | 设计 |
|---|---|
| Rubric | 0 完全错误 / 1 部分相关 / 2 大体正确 / 3 完全正确（写进 `prompts/judge/system.txt`） |
| 调用 | `temperature=0`、`response_format=json_object` |
| 隔离 | 裁判模型与待测模型不同（避免自评偏置） |
| 错误分类 | `llm_error` / `parse_error` / `empty_answer` / `run_error` |
| 短路 | 答案为空 → 直接 `empty_answer`，不调裁判；被测失败 → `run_error` 透传 |
| 输出 | `score`(0–3)、`reason`、`error_type` |

**验证**：人工抽 10 条与裁判分对比，一致率 ≥ 70%（首版目标，后续迭代）。

#### 4.10 CI 评测门禁

| 层 | 触发 | 内容 | 是否阻塞 |
|---|---|---|---|
| `eval-smoke` | PR（可选标签） | 5 条固定样本，跑通链路 + 分数在预期区间 | 不阻塞（先观察） |
| `eval-nightly` | 每天 02:00 | 全量 50–100 条 + 与上一轮对比 | 阻塞（分数下降 > 5% 告警） |
| `prompt-contract` | PR | 渲染后的 Prompt 无残留 `{占位符}`、JSON Schema 校验通过 | 阻塞 |

## 5. 预测效果

> 以下为**按代码逻辑推导的确定性结果**与**基于当前规模的估算**，标注了测量方式；非拍脑袋数字。

### 5.1 确定性收益（改完即成立）

| 指标 | 现状 | 目标 | 测量方式 |
|---|---|---|---|
| 报告洞察覆盖率 | 0%（永远为空） | 100%（有洞察数据时） | 生成 comprehensive 报告，检查 `data.insight != null` |
| 成本记录完整度 | 每任务仅 1 行（互相覆盖） | 每次 LLM 调用 1 行 | `SELECT count(*) FROM llm_calls WHERE task_id=?` 对比实际调用次数 |
| 重试执行率 | 0%（只改状态） | 100% | 点重试后 `celery_task_id` 变化且任务终态为 `completed` |
| 取消生效时延 | 不生效（跑完为止） | ≤ 1 个条目处理时间 | 取消后观察 worker 停止时间 |
| 报告任务可见性 | 不在任务列表 | 与其余 4 类一致 | `GET /tasks?task_type=report` 非空 |

### 5.2 估算收益（依赖数据规模，标注假设）

| 指标 | 假设 | 预估变化 |
|---|---|---|
| 成本统计准确度 | demo：3 个 raw + 100 条评估 | 记录行数 1 → 103（+10 200%）；金额误差从 −99% 收敛到 ≈0 |
| 大文件数据完整性 | 上传 30 万字符 CSV | 清洗条目数从「前 20 万字符对应行数」→ 全量行数 |
| 限流准确性 | Nginx 反代 + 3 个并发用户 | 从「全站共用一个桶」→ 每 IP 独立（3 个桶） |
| 知识库稳定性 | LLM 返回空 faqs | 种子 FAQ 保留率 100%（当前为 0） |
| 质量可验证性 | 50 条 Golden Set | 从「无基准」→ 可回答「本次改动 ±X 分」，噪声约 ±3–5 分（50 条规模） |

> 说明：50 条样本的置信区间较宽，只能判断方向性变化（≥5 分差异），不能宣称小幅度提升。若需更细粒度，需扩到 200 条以上。

### 5.3 定性收益

- **可解释性**：每个数字都能追溯到「哪版 Prompt、哪个模型、哪次任务」。
- **可回归性**：改 Prompt/换模型后有客观对比，不再靠感觉。
- **可演示性**：洞察页、评测看板、成本卡片让能力被看见（对面试/评审尤其重要）。
- **可维护性**：任务、成本、报告三套数据口径统一，减少「看起来对但算错了」的隐性 bug。

### 5.4 不确定性

| 风险点 | 说明 |
|---|---|
| 裁判一致性 | 首版裁判与人工一致率可能只有 60–70%，需要 1–2 轮 rubric 调整 |
| 成本上升 | 评测跑批会消耗真实 token；建议用 BYOK Key 或单独预算，nightly 限制在 100 条内 |
| 前端工作量 | 4 个页面/模块，实际工时可能超出估算 30% |

## 7. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 迁移 012 改 `data_id` 可空 | 历史 `quality` 数据不受影响，但依赖 NOT NULL 的代码可能报错 | 全仓 grep `data_id` 使用点；测试覆盖 |
| 迁移 012 改 `timestamp` 可空 | 趋势图/列表排序可能出现空值 | 前端过滤 `timestamp IS NOT NULL` 并显示「未标注时间」；洞察/报告统计显式排除空时间 |
| 唯一约束建立前的历史重复数据 | 迁移可能因重复失败 | 迁移内先按 `ctid` 去重（保留最新），再建唯一索引；迁移前备份 |
| 成本键变更导致历史与新增口径并存 | 报表短期出现两种键格式 | 报表按 `created_at` 过滤；文档注明切换时间点 |
| 取消引入 revoke | 可能中断正在写库的事务 | `terminate=False` + 循环内检查，不强制杀进程 |
| 评测消耗真实 token | 成本上升 | nightly 限 100 条；优先用 BYOK Key；`DAILY_COST_LIMIT` 兜底 |
| 裁判与业务模型同源 | 自评偏置 | 裁判模型与业务模型分离（配置项 `JUDGE_MODEL`） |
| 前端工作量超预期 | 排期延后 | 阶段三按页面拆分为 4 个独立 PR，可单独交付 |

### 11.3 与计划的差异

1. **demo 保护未新增错误码**：`core/errors.py` 明确「28 条业务错误码不得自造」，
   故复用 `AUTH_FORBIDDEN`（403）+ `details.reason=demo_account_protected`，
   而非计划中提到的 `DEMO_ACCOUNT_PROTECTED`。
2. **`pg_insert` 用表对象**：`pg_insert(CleanedData)` 的 `values(metadata=...)` 会与
   ORM 的 `metadata` 属性冲突，改用 `pg_insert(CleanedData.__table__)`。
3. **单次长调用也复查取消**：报告/洞察/知识提取在 Agent 返回后额外查一次状态，
   避免 `cancelled` 被收尾逻辑覆盖（计划只写了 revoke + 入口检查）。

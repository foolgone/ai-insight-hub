## 一、测试目标与口径

### 1.1 核心目标

- **质量保障**：确保代码质量与系统稳定性
- **快速反馈**：尽早发现问题，降低修复成本
- **持续集成**：CI 自动执行，门禁可量化
- **文档化**：测试即文档，描述系统真实行为

### 1.2 量化口径

| 测试类型 | 目标 | 是否进 CI 门禁 | 执行频率 |
|---------|------|--------------|---------|
| **单元测试** | 覆盖率 ≥ 80% | ✅ `--cov-fail-under=80` | 每次 push / PR |
| **集成测试** | 覆盖率 ≥ 60% | ⬜ 仅评审目标，未单独设门禁 | 每次 push / PR |
| **Prompt 测试** | 每 Agent ≥ 50 用例，每维度 ≥ 10 用例 | ⬜ CI 默认排除（`-m "not prompt"`） | Prompt/Agent 变更时手动或定时 |
| **前端单元测试** | 覆盖率 ≥ 80% | ⬜ 待 `coverage.thresholds` 配置后生效 | 每次 push / PR |
| **E2E 测试** | 关键流程 100% 覆盖（当前 8 条） | ⬜ 本地已落地（T1），CI 化 Phase 2 | 部署前 / 关键改动后 |
| **性能测试** | 核心 API P95 < 2s | ⬜ 部署前手动 | 每周 / 部署前 |

**覆盖率口径说明**：

1. 当前 CI（`.github/workflows/test.yml`）执行 `pytest -m "not prompt" --cov=app --cov-fail-under=80`，即**单元测试 + 集成测试合并计算 80%**，不区分两层。
2. 表中「集成测试 ≥ 60%」是**分层评审目标**，用于判断集成层是否覆盖了主要 API 契约，不单独配置门禁。
3. 前端覆盖率门禁已在 `vitest.config.js` 配置 `coverage.thresholds`（行/函数/语句 80、分支 70），`@vitest/coverage-v8` 已在 devDependencies（见 [04-前端测试规范](./04-前端测试规范.md) 第 2 章）。

## 二、测试分层

### 2.1 测试金字塔

```
              ┌─────────────────┐
              │   E2E 测试      │  5%   (慢，昂贵，全链路)
              │  关键流程验证    │
              └─────────────────┘
                     ↑
          ┌──────────────────────┐
          │    集成测试           │  25%  (中速，API+DB+Redis)
          │  模块间协作验证       │
          └──────────────────────┘
                     ↑
     ┌────────────────────────────────┐
     │       单元测试                  │  70%  (快，隔离，细粒度)
     │  函数/类级别验证               │
     └────────────────────────────────┘
```

### 2.2 各层职责与工具映射

| 层级 | 范围 | 依赖策略 | 工具（仓库实际） |
|------|------|---------|----------------|
| **单元测试** | 单个函数/类/组件 | 不连真实 DB/Redis/LLM，全部 mock | pytest 7.4.4 + pytest-mock + pytest-asyncio；前端 Vitest `^1.1.3` |
| **集成测试** | API + Service + DB + Redis | 真实 PostgreSQL（pgvector）+ Redis，**不 mock** | pytest 7.4.4 + `fastapi.testclient.TestClient`（httpx 0.26.0） |
| **Prompt 测试** | Agent 输入输出契约 | 真实 DeepSeek V4.1 Flash（`ChatDeepSeek`） | pytest 7.4.4 + sentence-transformers 2.3.1 |
| **E2E 测试** | 前端 → 后端 → DB | 真实服务栈（前端 5173 + 后端 8000 + PG/Redis） | Playwright `^1.64`（`frontend/e2e/`，本地用系统 Edge；CI 化 Phase 2） |
| **性能测试** | 核心 API 响应时间 | 真实服务栈 | locust 2.20.0 |

### 2.3 pytest marker 约定

`backend/pytest.ini` 已定义四个 marker（`--strict-markers` 已开启，未注册的 marker 会直接报错）：

| marker | 含义 | 默认是否执行 |
|--------|------|------------|
| `unit` | 单元测试，不依赖外部服务 | ✅ |
| `integration` | 集成测试，需真实 PostgreSQL/Redis | ✅（需先启动 `docker-compose.test.yml`） |
| `prompt` | Prompt 测试，需真实 LLM | ❌ CI 用 `-m "not prompt"` 排除 |
| `slow` | 慢速测试 | ✅（可用 `-m "not slow"` 排除） |

> `asyncio_mode = auto` 已开启，异步测试函数**无需**再加 `@pytest.mark.asyncio`。

## 三、各层测试要点

### 3.1 后端单元测试

- 范围：Agent 纯逻辑（解析/脱敏/评分归一化）、Service、Utils
- 原则：**不连库**。数据库用 `unittest.mock.Mock()`，LLM 用 `mock.patch` 替换 `ChatDeepSeek.invoke`
- 详细规范：[01-后端单元测试规范](./01-后端单元测试规范.md)

### 3.2 后端集成测试

- 范围：API 契约、DB 事务与级联、Celery 任务、Agent 链式调用
- 原则：使用真实 PostgreSQL（`aiinsight_test`，端口 5433）与 Redis（6380）
- 详细规范：[02-后端集成测试规范](./02-后端集成测试规范.md)

### 3.3 Prompt 测试

- 范围：输出结构（JSON schema）、字段取值、语义相似度、注入防御、Token 消耗
- 原则：确定性字段精确匹配，自然语言字段用语义相似度或 LLM-as-judge，**不做全文精确匹配**
- 详细规范：[03-Prompt测试规范](./03-Prompt测试规范.md)

### 3.4 前端测试

- 范围：组件渲染与交互、Hook、API mock、响应式断点、可访问性手工检查
- 原则：Vitest + Testing Library，模块级 `vi.mock`，纯 JS（`.jsx`），无 TypeScript
- 详细规范：[04-前端测试规范](./04-前端测试规范.md)

## 四、测试环境

### 4.1 本地 / CI 环境对照

| 环境 | 用途 | PostgreSQL | Redis | 对象存储 |
|------|------|-----------|-------|---------|
| **本地开发** | 开发调试 | `docker-compose.yml`（5432） | `docker-compose.yml`（6379） | MinIO（`docker-compose.yml`） |
| **本地测试** | 集成测试 | `docker-compose.test.yml` → `postgres-test`（**5433**） | `redis-test`（**6380**） | 不使用（测试不依赖对象存储） |
| **CI** | 自动化测试 | GitHub Actions service `pgvector/pgvector:pg14`（5432） | service `redis:7-alpine`（6379） | 不使用 |
| **Staging / Production** | 部署 | 云数据库 | 云 Redis | 云对象存储 |

### 4.2 `docker-compose.test.yml` 实际内容

```yaml
version: '3.8'

services:
  postgres-test:
    image: pgvector/pgvector:pg14
    container_name: aiinsight-postgres-test
    environment:
      POSTGRES_USER: aiinsight
      POSTGRES_PASSWORD: dev_password
      POSTGRES_DB: aiinsight_test
    ports:
      - "5433:5432"
    volumes:
      - ./backend/scripts/init_db.sql:/docker-entrypoint-initdb.d/init_db.sql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U aiinsight"]
      interval: 5s
      timeout: 5s
      retries: 10

  redis-test:
    image: redis:7-alpine
    container_name: aiinsight-redis-test
    ports:
      - "6380:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
```

**注意**：

- 测试库名为 `aiinsight_test`（**不是** `ai_insight_hub_test`），用户 `aiinsight`，密码 `dev_password`
- 没有 `tmpfs` 内存盘，也没有 `minio-test` 服务——测试不依赖对象存储
- `init_db.sql` 负责创建 `vector` / `pg_trgm` 扩展，首次启动自动执行

### 4.3 测试数据管理

- **单元测试**：全部使用内存构造的对象或 `Mock()`，**不写库**
- **集成测试**：每个用例独立事务，结束后回滚；跨用例共享的数据通过 factory 在用例内创建
- **Prompt 测试**：输入用例与 golden 输出放在 `backend/tests/prompt/`，基准文件随代码提交

## 五、CI 集成

### 5.1 实际工作流

仓库只有**一个**测试工作流：`.github/workflows/test.yml`（触发条件：push 到 `main`、任意 PR）。下面为**节选**（省略了 services 的 `options` healthcheck 块，完整内容以文件为准）：

```yaml
name: Test

on:
  push:
    branches: [main]
  pull_request:

jobs:
  backend:
    name: 后端测试
    runs-on: ubuntu-latest
    services:
      postgres:
        image: pgvector/pgvector:pg14
        env:
          POSTGRES_USER: aiinsight
          POSTGRES_PASSWORD: dev_password
          POSTGRES_DB: aiinsight_test
        ports:
          - 5432:5432
      redis:
        image: redis:7-alpine
        ports:
          - 6379:6379
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
          cache: pip
      - name: 安装依赖
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt -r requirements-dev.txt
      - name: 准备测试库扩展
        run: |
          PGPASSWORD=dev_password psql -h localhost -U aiinsight -d aiinsight_test -f scripts/init_db.sql
      - name: 单元测试 + 覆盖率（阈值 80%）
        env:
          DATABASE_URL: postgresql://aiinsight:dev_password@localhost:5432/aiinsight_test
          REDIS_URL: redis://localhost:6379/0
        run: pytest -m "not prompt" --cov=app --cov-report=term-missing --cov-fail-under=80
      - name: 代码质量
        run: |
          black --check app tests
          flake8 app tests

  frontend:
    name: 前端测试
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: npm
          cache-dependency-path: frontend/package-lock.json
      - name: 安装依赖
        run: npm ci
      - name: Lint
        run: npm run lint
      - name: 单元测试 + 覆盖率
        run: npm run test:coverage
```

### 5.2 门禁现状

| 阶段 | 实际门禁 | 失败策略 |

| **PR 合并** | 后端 `pytest -m "not prompt"` 且覆盖率 ≥ 80%；`black --check`、`flake8`；前端 `npm run lint`、`npm run test:coverage` | 阻止合并 |
| **部署 Staging** | 全量测试 + 人工回归 | 阻止部署 |
| **部署 Production** | 全量测试 + 性能测试 | 阻止部署 |

**尚未落地的门禁**（需补，见第八章）：

- Prompt 测试的定时执行（`-m prompt`）
- 前端覆盖率阈值（`@vitest/coverage-v8` 未安装）

## 七、Prompt 回归门禁与成本控制

Prompt 测试的价值在**回归**，因此需要三类机制（当前均为**设计口径，尚未实现**）：

### 7.1 Golden 基线比对

- 基线文件：`backend/tests/prompt/golden_outputs/*.json`，随代码提交
- 比对方式：
  - **确定性字段**（`user_message`、`ai_response`、`tags` 等结构化结果）→ 精确匹配
  - **自然语言字段**（摘要、建议文案）→ 语义相似度 ≥ 阈值，或 LLM-as-judge 打分
- 更新流程：`REGENERATE_GOLDEN=1` 生成候选 → **人工 diff 审查** → 确认无误后提交

### 7.2 LLM-as-judge

用于无法用规则判定的输出质量（如洞察结论是否切题）：

- 判定模型：与生产同源的 DeepSeek V4.1 Flash，`temperature=0`
- 判定 Prompt 独立存放，避免与被测 Prompt 耦合
- 判定结果落库（`llm_calls` 表），可回溯

### 7.3 调用预算上限

Prompt 测试会真实调用 LLM，必须有成本闸门：

| 控制项 | 建议口径 | 落地方式 |
|-------|---------|---------|
| 单用例 Token 上限 | 输入 < 2000 / 输出 < 1000 | 用例内断言 `usage` |
| 单次全量用例数上限 | 每 Agent ≤ 200 | 参数化用例总数校验 |
| 单次运行成本上限 | 待确认（按 DeepSeek 定价与用例数估算） | 运行前预估 + 超限中止 |
| CI 执行频率 | 不随每次 push 执行 | 定时任务或手动触发 |

> 成本上限的具体金额**待确认**（确认方式：以 DeepSeek 官方当前定价 × 全量用例平均 Token 实测值计算，实测后回写本表）。

## 十、常见问题

### Q1: 单元测试能不能连数据库？

**A**: 不能。单元测试层要求**不依赖外部服务**，数据库用 `Mock()`，LLM 用 `mock.patch` 替换 `ChatDeepSeek.invoke`。需要真实数据库的用例一律归到 `integration`，用 `docker-compose.test.yml` 起 `aiinsight_test`（端口 5433）。

### Q2: 如何降低 LLM 输出的不确定性？

**A**: DeepSeek 支持 `temperature` 参数，但**没有 `seed` 参数**，因此：

1. `temperature=0` 降低随机性（不能消除）
2. 确定性字段做精确匹配，自然语言字段做语义相似度 / LLM-as-judge
3. 同一用例重复执行 N 次，要求结果**结构一致**（不要求逐字一致）

```python
# 正确：只固定温度，不传 seed
from langchain_deepseek import ChatDeepSeek

llm = ChatDeepSeek(model="deepseek-chat", temperature=0)
```

### Q3: 如何加速慢速测试？

**A**:

1. Mock 外部依赖（LLM、第三方 API）
2. 单元测试层不连库（不要用 SQLite 顶替 PostgreSQL——两者在 `JSONB`、`pg_trgm`、`vector` 上行为不同，会掩盖真实问题）
3. 并行执行：`pytest -n auto`（pytest-xdist 3.5.0 已装）
4. 用 marker 分离：`-m "not slow"`、`-m "not prompt"`

```python
@pytest.mark.slow
def test_heavy_computation():
    pass
```

```bash
pytest tests/unit -m "not slow"
```

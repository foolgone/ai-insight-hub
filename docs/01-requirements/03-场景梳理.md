## 1. 梳理方法

### 1.1 来源

本文档不从零设计场景，而是把需求讨论中的 5 项核心需求，按「谁在什么情况下、要解决什么问题、完成的标准是什么」展开成可开发的场景：

| 来源 | 提取内容 |
|---|---|
| [`00-需求讨论记录.md`](./00-需求讨论记录.md) 核心需求 1-5 | 数据清洗、质量评估、知识库构建、诉求收集、报告生成 |
| 同上「数据隔离需求」 | 每个数据源独立导入、独立分析、独立配置、互不干扰 |
| 同上「定制化操作需求」 | 每个数据源可自选分析流程（可跳过知识提取等步骤） |
| [`01-产品概述.md`](./01-产品概述.md) 第 4 节 | 三类目标用户：AI 产品经理、客服运营、数据分析师 |

### 1.2 判定标准

一个场景进入 MVP，需同时满足：

1. 在需求讨论中有明确出处（不是凭空补充）
2. 有清晰的角色与触发时机（谁、什么时候用）
3. 有可判定的完成状态（能写验收标准）

### 1.3 尚未验证的假设

以下均为**假设**，需用户调研确认（见 [`02-用户调研.md`](./02-用户调研.md)）：

- 使用频率（每天 / 每周 / 按需）—— 讨论记录中列为待确认
- 数据规模（单次导入多少条对话）
- 用户是否接受「异步任务 + 稍后查看结果」的交互方式
- 三类用户中谁是主要买单角色

## 3. 场景详情

### S1｜第三方对话数据接入与清洗标准化

**角色**：数据分析师

**触发时机**：从第三方客服系统导出一批对话数据，需要变成可分析的统一格式时

**痛点**（来自需求讨论）：
- 第三方数据格式不统一（Excel / CSV / JSON / 数据库导出）
- 数据质量参差不齐，存在重复对话、缺字段
- 人工清洗耗时，且每次都要重写脚本

**目标**：把「一堆格式各异的原始文件」在尽量少的人工干预下，变成「字段齐全、合法 JSON、已去重」的对话数据

**主流程**：
```
创建数据源 → 上传文件（CSV/JSON/Excel/TXT）→ 触发清洗（异步）
→ AI 解析 + 字段标准化 + 去重 → 查看清洗结果与质量报告 → 确认入库
```

**输入 / 输出**：

- 输入：单次上传 ≤ 50 MB（见 `.env.example` 的 `MAX_UPLOAD_SIZE_MB`），扩展名 `csv,json,xlsx,txt`
- 输出：逐条对话 JSON（`dialogue_id` / `timestamp` / `user_message` / `ai_response` 四字段必填）+ 质量评分（0–100）+ 问题标记

**完成标准**（与需求讨论记录中的验收标准对应）：
- 基线样本集上解析成功率 ≥ 95%
- 完全重复记录去重后残留 0 条，相似对话去重准确率 > 90%

**开放问题**：
- 单批数据量上限与处理时长预期（待实测）
- 清洗失败时是整批回滚，还是部分成功 + 失败明细

---

### S2｜AI 客服质量评估与人工复核

**角色**：AI 产品经理（主导）、客服运营（复核）

**触发时机**：清洗完成一批对话后，需要判断「AI 客服回答得好不好、哪里有问题」

**痛点**：
- 人工抽查覆盖率低（< 5%）、滞后
- 缺少统一评分口径，不同人打分不可比
- 幻觉、越界承诺难以系统性发现

**目标**：对每条对话给出 5 维评分与问题标注，低分样本自动进入人工复核队列

**主流程**：
```
选择数据源 → 触发评估（异步）→ 按 5 维打分（0-100）
→ 低分/低置信度样本进入人工复核队列 → 人工确认或驳回 → 记录反馈
```

**评估维度**（与 [`01-产品概述.md`](./01-产品概述.md) 第 3 节一致，5 维）：
`accuracy`（准确性）/ `completeness`（完整性）/ `tone`（语气与体验）/ `compliance`（合规性）/ `hallucination`（幻觉）

**输入 / 输出**：

- 输入：已清洗的对话
- 输出：单条评分 + 维度分 + 问题标记 + 改进建议 + 风险预警（如「价格承诺越界」）

**完成标准**：
- 每条输出 5 维齐全、分值 0–100，缺维度即不通过
- 与人工总分差 ≤ 10 分的样本占比 ≥ 80%
- 单条评估耗时 ≤ 2 秒（P95）

**开放问题**：
- 人工复核队列的容量与 SLA（多久内必须处理完）
- 评分阈值分级（如 < 60 必复核）需与 `needs_review` 口径统一

### S3｜知识库智能构建与盲区发现

**角色**：AI 产品经理

**触发时机**：积累了一定量的对话后，需要决定「知识库该收录什么、还缺什么」

**痛点**：
- 手动维护知识库，靠拍脑袋决定收录内容
- 不知道哪些问题 AI 答不上来（盲区）
- 知识过时不敏感

**目标**：从真实对话中自动提取可入库的 FAQ，并给出带优先级的知识盲区清单

**主流程**：
```
选择数据源 → 触发知识提取（异步）→ 聚类相似问题 → 生成 FAQ 候选
→ 发现盲区（未覆盖 / 答案不完整）→ 按优先级排序 → 人工确认入库
```

**输入 / 输出**：

- 输入：已清洗 + 已评估的对话
- 输出：FAQ 候选列表（JSON / Markdown）、盲区清单（含关联对话 id、缺失原因、P0/P1/P2 优先级）、更新建议

**完成标准**：
- FAQ 候选经人工判定「可直接入库」的比例 ≥ 80%
- 知识盲区覆盖率 ≥ 85%（定义见 [`01-产品概述.md`](./01-产品概述.md) 第 7 节）
- 每条盲区必须带关联对话 id 与优先级，缺字段即不合格

**开放问题**：
- FAQ 的「标准答案」以 AI 回复为准还是人工重写
- 知识过时检测的判定规则（时间衰减？业务变更事件？）—— 待定义

---

### S4｜客户诉求收集与洞察分析

**角色**：客服运营

**触发时机**：需要向产品或管理层说明「客户到底在抱怨什么、最近有什么新问题」时

**痛点**：
- 诉求散落在对话里，靠人工读几百条无法汇总
- 客诉升级（愤怒情绪）发现不及时
- 高频问题与转人工场景缺少量化依据

**目标**：把对话自动归类为咨询 / 投诉 / 建议，识别情感与痛点，输出可行动清单

**主流程**：
```
选择数据源 → 触发洞察分析（异步）→ 诉求分类 + 情感判定
→ 痛点聚类（未解决 / 反复出现 / 高转人工）→ 生成洞察结论
```

**输入 / 输出**：

- 输入：已清洗的对话（可选结合运营侧数据：转人工率、解决率——来源待确认）
- 输出：诉求分布、高频问题排行、情感趋势、痛点清单、产品改进建议

**完成标准**：
- 三分类（咨询 / 投诉 / 建议）准确率 ≥ 85%，并导出混淆矩阵
- 每条诉求带 `category` + `sentiment` 字段，缺失即不合格
- 「愤怒」类情感召回率 ≥ 90%（阈值待确认）

**开放问题**：
- 情感粒度是 4 类（满意/中性/不满/愤怒）还是更细
- 「高转人工场景」所需的数据是否可获取（依赖第三方系统字段）

---

### S5｜数据分析报告生成与导出

**角色**：数据分析师（制作）、AI 产品经理 / 管理层（阅读）

**触发时机**：周会 / 月度复盘 / 向上汇报前

**痛点**：
- 报告靠手工拼 Excel + PPT，耗时长
- 每次口径不一致，跨期不可比
- 结论靠人工写，容易漏掉关键问题

**目标**：基于已有分析结果，一键生成结构化的多格式报告

**主流程**：
```
选择数据源与分析结果 → 选择报告类型 → 生成报告（异步）
→ 在线预览（Markdown）→ 导出（PDF / Excel）
```

**输入 / 输出**：

- 输入：某数据源下的评估结果 / 知识库结果 / 洞察结果
- 输出：4 类报告 —— AI 质量报告、知识库健康报告、客户洞察报告、运营数据报告
- 导出格式：PDF、Excel、Markdown（PPT 是否纳入**待确认**）

**完成标准**：
- 4 类报告各生成 1 份，必填章节非空、无 `[记录]`/`TODO`/`XXX` 占位符
- 三种格式各导出 1 次并校验可打开；生成耗时阈值待实测

**开放问题**：
- 报告模板是固定 4 套，还是允许用户自定义章节
- 是否需要报告版本对比（本期 vs 上期）

## 4. 贯穿性需求

这两个需求不单独成场景，但 S1–S5 都必须满足。

### 4.1 数据源隔离

来自需求讨论「数据隔离需求」（借鉴 chat-resume 的「每份简历独立」）：

- 每个数据源（DataSource）独立导入、独立分析、独立报告
- 数据源之间互不可见、互不干扰
- 典型切分方式：按月（2026 年 1 月 / 2 月）、按渠道（电商平台 / APP 内）

### 4.2 定制化流程

来自需求讨论「定制化操作需求」：

- 同一套能力，不同数据源可只跑其中几步，例如：
  - 客服对话：清洗 → 评估 → 知识提取 → 报告
  - 销售话术：清洗 → 评估 → 报告（跳过知识提取）
  - 内容审核：清洗 → 风险评估（不同评估标准）→ 报告
- 评分标准、标签、分析规则可按数据源配置

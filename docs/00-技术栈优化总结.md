
---

## ✅ 优化理由

### 1. **部署简化**
- ❌ 优化前：需要部署 4 个数据服务
- ✅ 优化后：只需部署 3 个数据服务
- **减少 25% 的基础设施**

### 2. **维护成本降低**
- ❌ 优化前：需要维护 PostgreSQL + ChromaDB 两套数据库
- ✅ 优化后：只维护 PostgreSQL 一套
- **减少 50% 的维护工作**

### 3. **事务一致性**
- ❌ 优化前：跨数据库操作，无法保证 ACID
- ✅ 优化后：单数据库事务，完全 ACID
- **数据一致性更强**

### 4. **查询性能**
- ❌ 优化前：需要应用层关联 PostgreSQL 和 ChromaDB 的数据
- ✅ 优化后：直接 SQL JOIN，性能更好
- **减少网络往返**

### 5. **数据量适配**
- 项目预估：~50,000 FAQ + 部分对话向量
- pgvector 性能：轻松支持 100万+ 向量
- **完全满足需求**

## 🔧 技术实现

### PostgreSQL + pgvector 配置

**1. 安装扩展**
```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

**2. 创建向量列**
```sql
CREATE TABLE knowledge_base (
    id UUID PRIMARY KEY,
    question TEXT NOT NULL,
    answer TEXT NOT NULL,
    embedding VECTOR(384)  -- paraphrase-multilingual-MiniLM-L12-v2 输出维度（384 维）
);
```

> 此处仅列出核心字段，完整表结构以 `docs/03-architecture/03-数据库设计.md` §3.6 为准。

**3. 创建向量索引**
```sql
-- HNSW 索引（本项目采用：读多写少，召回率与延迟更优）
CREATE INDEX idx_kb_embedding_hnsw ON knowledge_base 
    USING hnsw (embedding vector_cosine_ops);

-- IVFFlat 索引（备选方案：仅在向量量级很大且内存受限时使用；
-- 与 HNSW 二选一，不要同时建在同一个 embedding 列上）
-- CREATE INDEX idx_kb_embedding ON knowledge_base
--     USING ivfflat (embedding vector_cosine_ops)
--     WITH (lists = 100);
```

**4. 相似度搜索**
```sql
-- 余弦相似度搜索
SELECT question, answer,
       1 - (embedding <=> $1) AS similarity
FROM knowledge_base
ORDER BY embedding <=> $1
LIMIT 10;
```

## 📈 性能对比

### 向量搜索性能

| 指标 | ChromaDB | pgvector (IVFFlat) | pgvector (HNSW) |
|------|----------|-------------------|----------------|
| **检索速度** | ~50ms | ~30ms | ~10ms |
| **插入速度** | 快 | 中 | 慢 |
| **索引构建** | 快 | 中 | 慢 |
| **内存占用** | 中 | 低 | 高 |
| **最佳场景** | 独立向量库 | 平衡场景 | 读多写少 |

**结论**：对于 AI Insight Hub（读多写少），pgvector HNSW 索引更优

> 说明：上表检索速度等数值为**量级示意**（不同硬件、维度、数据量差异很大），本项目未做实测；正式选型依据以 POC 实测结果为准（见 `04-development/04-开发方案.md` 的 pgvector POC）。

## 🚀 迁移步骤

如果未来需要从 ChromaDB 迁移到 pgvector：

**1. 导出 ChromaDB 数据**
```python
collection = client.get_collection("knowledge_base")
data = collection.get(include=["documents", "embeddings", "metadatas"])
```

**2. 导入到 PostgreSQL**
```python
async def insert_batch(db, data):
    """在 async 函数内执行；asyncpg 使用 $1/$2 位置参数，不支持 :name 命名参数"""
    for i in range(len(data["ids"])):
        await db.execute(
            """
            INSERT INTO knowledge_base (id, question, answer, embedding)
            VALUES ($1, $2, $3, $4)
            """,
            data["ids"][i],
            data["documents"][i],
            data["metadatas"][i]["answer"],
            data["embeddings"][i],
        )
```

**3. 创建索引**
```sql
CREATE INDEX idx_kb_embedding_hnsw ON knowledge_base
    USING hnsw (embedding vector_cosine_ops);
```

## 🎯 何时需要 ChromaDB？

**只在以下情况考虑 ChromaDB**：

1. ✅ 向量数据量 > **1000万**
2. ✅ 需要独立的向量搜索服务
3. ✅ 需要多模态向量（图片、音频等）
4. ✅ 需要 ChromaDB 特有功能

**AI Insight Hub 不需要**：
- ❌ 向量数据量：~50K FAQ（很小）
- ❌ 不需要独立服务
- ❌ 只有文本向量
- ❌ pgvector 完全够用

## 💡 最佳实践

### 1. **向量维度选择**

**本项目冻结口径：384 维**，嵌入模型 `paraphrase-multilingual-MiniLM-L12-v2`（Sentence Transformers，免费、可离线）。

```python
# ✅ 本项目采用：paraphrase-multilingual-MiniLM-L12-v2（384 维）
embedding = VECTOR(384)

# 说明：不要再使用 1536 维（那是旧嵌入模型的维度，与本项目 384 维模型不匹配）；
# 向量维度必须与嵌入模型输出维度一致，否则写入会直接报错。
```

### 2. **索引选择**
```sql
-- 本项目采用：HNSW（读多写少，延迟与召回更优）
CREATE INDEX idx_kb_embedding_hnsw ON knowledge_base
    USING hnsw (embedding vector_cosine_ops);

-- 备选：IVFFlat（向量量级很大、内存受限时二选一）
-- CREATE INDEX idx_kb_embedding ON knowledge_base
--     USING ivfflat (embedding vector_cosine_ops)
--     WITH (lists = 100);
```

### 3. **查询优化**
```sql
-- HNSW 检索深度：默认 40，越大越精确但越慢
SET hnsw.ef_search = 40;

-- 若改用 IVFFlat，则改调探测列表数
-- SET ivfflat.probes = 10;  -- 默认 1，越大越精确但越慢

-- 相似度搜索
SELECT * FROM knowledge_base
ORDER BY embedding <=> $1
LIMIT 10;
```
